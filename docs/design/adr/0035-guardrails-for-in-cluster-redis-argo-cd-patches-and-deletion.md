### 2. The new checks

Check 1 also blocks, in every spelling and wrapper the hook already handles:

1. **`argocd app confirm-deletion`**, with any options and arguments. The hook finds it as it finds the deleting argocd subcommands of ADR 0028 §5 item 2: the parent `app` and the subcommand are positional words after the options it knows to take a value, and an unknown option right after `app` may take the next word, so the positional word after that one counts as the subcommand too.
2. **An `argocd app patch-resource` that the `oc patch` rule would refuse**: its words name `finalizers`, or name `persistentVolumeReclaimPolicy` together with `Delete`, `Recycle` or a shell expansion in the same word, compared in lower case (ADR 0028 §5 item 3), or replace or remove a whole object or its metadata (see the readings below). Every word after `argocd` is read, so the patch counts wherever `--patch` stands, for every `--kind` and every `--patch-type`. The subcommand is found as in item 1, with `--patch` and `--patch-type` added to the value options the hook skips. A harmless patch and `Retain` stay allowed, and so do the subcommands that only read (`app get-resource`, `app resources`, `app manifests`).
3. **The deletion-approved annotation**, the answer's "annotation spelling": setting the annotation that `argocd app confirm-deletion` writes, which Argo CD's documentation gives as the manual way to approve. The hook blocks:
   - an `oc annotate` or `oc patch` with a word that names `deletion-approved`, compared in lower case, on any resource and with any value, its removal (`argocd.argoproj.io/deletion-approved-`) included, as the patch rule matches finalizer additions too. Matching the last part of the key also finds a JSON patch path, which writes `argocd.argoproj.io~1deletion-approved`;
   - any `argocd` command whose words name `deletion-approved`. The maintainer's answer to D109 confirms this reading of "the annotation spelling" as built: every way to set it that the command text shows, and Argo CD has three besides confirm-deletion: `argocd app patch`, `argocd app patch-resource` of an Application, and `argocd app create --upsert --annotations`. The hook does not tell them from a command that only prints such a key (`argocd app list --selector deletion-approved=yes`), nor from one in which `argocd` is only an argument (`grep -rn argocd docs/deletion-approved.md`), as every argocd check has read since ADR 0028 (`echo argocd app delete x` is blocked too). It does not look for the subcommand either, so no unknown option before it can hide a writer (`argocd app --repo <url> --path <dir> create backend3 --upsert --annotations argocd.argoproj.io/deletion-approved=now`). An agent reads the key by piping argocd's output to `grep` or `jq`, or with `oc get`.

   `oc get` and `oc describe` of the annotation, and an `oc annotate` or `oc patch` of any other key, Argo CD's own `argocd.argoproj.io/refresh` included, stay allowed.

Check 2 also:

4. **Blocks `redis-cli` run in the cluster**: in the command part of `oc exec`, `oc rsh` or `oc debug` (by any path, in quotes, after `env` or `timeout`, in a `sh -c` script, as rsh's `--shell`), and in text that they read on stdin (piped `echo` or `printf` output, a here-string, a heredoc), where the in-cluster rule of ADR 0028 §4 and §5 finds `psql`. It is blocked whatever its options and command, `redis-cli ping` included. A pod, container or namespace named like the client is not the command part, so it is not blocked by its name, and neither is a file named like it (`/data/redis-cli.log`). `redis-cli` does not join the listed commands of check 2, because those also get the target check on the agent's own host, and the answer keeps a `redis-cli` there allowed: the clusters' Redis answers on the agent's host only through a port-forward, which ADR 0028 §5 item 4 blocks. So a `redis-cli` in a pod that the agent starts itself (`oc run`, `oc create job`) is not blocked: it runs neither on the agent's host nor through `oc exec`, `oc rsh` or `oc debug`, the three routes the answer names. A `psql` there is still caught, by its target check. It is the client the clusters' Redis image ships; other Redis-protocol programs are not recognised (see "Negative and risks").
5. **Keeps the port-forward check as built** (D106): it knows the engines the clusters run, PostgreSQL, MySQL and Redis, by their ports, and never reads the pod or service name. A metrics or web port on a database Service, such as `svc/postgres` 9187, stays allowed. When a new engine is deployed, an amending ADR adds its ports and can cite D106's answer.

"In every spelling the hook already handles" needs the hook to read command text the way the programs read it. Each reading serves every check, ADR 0028's included. This follows oc, kubectl, the patch decoders, the API server, bash, argocd and `xargs`; it adds no rule:

- **Options before the oc verb.** oc finds its verb as cobra does: before the verb, an option that oc itself does not define as a boolean and that has no `=value` takes the next word as its value, also when only the verb defines it, and the verb then parses every word but itself, those before it included. oc 4.22 applies `oc -p '<patch>' patch pvc data`, `oc --type merge patch ...`, `oc --field-manager m annotate ...` and `oc --overwrite <key>=<value> annotate ...`, and `oc --wait pvc delete data` deletes the claim. So the hook reads the verb in two ways, its own (the first positional word after the options it knows to take a value) and cobra's, gives each verb its words both with and without the words before it, and lets every reading count. `--vmodule`, a global option of `oc options` that takes a value, and `oc get`'s value options `--sort-by`, `--chunk-size`, `-L`, `--label-columns` and `--subresource` join the value options the hook skips, so the type after them is still read (`oc get --sort-by .metadata.name pvc -o name | xargs oc delete`). When the oc 4.22 client is on the PATH, a test compares that list with the client's help.
- **Escapes in a patch.** kubectl reads a patch as YAML, of which JSON is a part, and both decoders turn an escape in a quoted string into its character: JSON's `\uXXXX` and `\/`, YAML's `\xXX`, `\uXXXX` and `\UXXXXXXXX`, and YAML's escaped line break, after an LF, a CR LF, a CR, or the NEL, LS or PS that go-yaml also reads as a line break. The patch rule of item 2 and the annotation rule of item 3 decode the escapes of ASCII characters and `\/`, and remove an escaped line break with the next line's indentation. The patch rule matches a word both as it is and with its spaces and tabs dropped and its line breaks kept, and the annotation rule with every blank dropped, so `fin\u0061lizers` and `deletion\u002dapproved` count, and so does a key or a block YAML value split by an escaped line break. Inside single quotes the shell keeps a `\` and its line break, which the hook removes first as a shell line continuation; the next line's indentation then stays in the word, and only the second reading still sees `path: "/meta\` and `    data"` as the path `/metadata` at the start of its line, also after a tag or an anchor (`path: !!str "/meta\`). The API server's JSON decoder reads `\/` as `/` in a patch that reaches it as written, as Argo CD sends `argocd app patch-resource`'s patch and kubectl a patch that starts with `{`, so `"path":"\/metadata"` through Argo CD replaces the metadata; kubectl's YAML decoder (go-yaml v2), which reads every other `-p` patch, refuses it, so there decoding it only errs towards blocking. A `Retain` written with an escape stays allowed.
- **Patches that replace a whole object or its metadata.** A JSON patch whose path is `""` (the whole object) or `/metadata` replaces or removes the finalizers along with everything else there, and the API server keeps the object's UID when the new metadata gives none (`BeforeUpdate`: "Use the existing UID if none is provided"). A strategic merge `$patch: replace` or `$patch: delete` replaces or empties the map it stands in, and `$retainKeys` keeps only the keys it lists (`handleDirectiveInMergeMap`, `applyRetainKeysDirective`). So the patch rule of ADR 0028 §5 item 3, and item 2 with it, count each of them as a finalizer change, in JSON or YAML, wherever a directive stands, since the hook cannot tell which map it is in. go-yaml, which kubectl uses for every patch that does not start with `{`, also accepts a tag, an anchor or a comment before a value (`path: !!str /metadata`, `$patch: &d delete`, `path: # all of it` with `/metadata` on the next line), which the rule skips, a comment up to the end of its line and a tag or an anchor also when the second reading of a patch, with its spaces removed, glues it to the value, and a block scalar or an alias as the value (`path: |-`, `path: *p`), which the rule does not read and so counts as such a patch. A tag with no value after it on its line, or before the `,` or `}` of a flow mapping, is the empty string for go-yaml (`path: !!str`), the path `""`, so it counts too, read in the patch as written, since the second reading glues a tag to the value after it. A JSON patch on a path below `/metadata`, such as `/metadata/labels/app`, and `$patch: merge` stay allowed.
- **Shell quoting.** bash decodes an ANSI-C quoted `$'...'` part (`\xHH`, `\NNN`, `\uHHHH`, `\UHHHHHHHH`, `\cX`, `\n` and the other escapes; a NUL ends it) and reads a `$"..."` part as double-quoted text. The hook's lexer does the same, and so does its fast path, which lexes every text with such a part. Its test for the program that reads a heredoc and the in-cluster rule's reading of a command part read such a text twice, with every quote and backslash removed, as ADR 0028 reads it, and part by part as the lexer reads it, and a match in either counts. A `$'` inside other quotes is text there, as in bash, so a NUL after it cannot cut off what follows (`echo "$'\0"; psql; echo "'"` still runs `psql`). So `oc delete $'\x6e\x73' web` is read as `oc delete ns web`.
- **Substitutions whose output the shell runs.** A shell, `source` or `.` that gets a process substitution reads its output as a script (`bash <(echo '...')`), and an unquoted `$(...)` or backquoted command where the command name goes runs its output as the command (`$(echo oc) delete ns web`), also in a `-c` or `eval` string (`eval "$(echo '...')"`). The hook finds that place as it finds kubectl's: after assignments, and anywhere after a runner word, with the runner's own options and values in between (`timeout 30 $(echo oc) delete ns web`). When that output is `echo` or `printf` text, the hook reads it as commands, as ADR 0028 §4 reads `echo` text piped into a shell, and in place of the command name its words take the substitution's place. After a runner's own words the substitution stays in front of them, because it may be one of those words, and the hook does not apply `printf` formats, so a check that counts an expansion as not checkable still sees it there. A double-quoted substitution in that place is its output as one word (`"$(echo oc)" delete ns web`), without the line breaks at its end, which bash removes from every substitution (`"$(printf 'oc\n')"`). That output stands only in the command's words: a `-c` string, a here-string and the text that `eval`, `ssh` or `watch` run again are read as written, so the commands that the substitution itself runs still count (`eval "$(echo x; oc delete ns web)"`). An `echo`'s own options (`-n`, `-e`, `-E` and their combinations) are not part of what it prints, as bash reads them, in that output, in piped text and in the text that `xargs` passes on. A `printf`'s `\n` and `\t`, which the hook reads as a line break and a tab in that output and in piped text, also end the word before a trigger word for the hook's fast path, so `printf 'ls\noc delete ns web\n' | sh` is read as ADR 0028 §4 reads piped `printf` text.
- **Other spellings that the programs accept.** `oc delete --raw` sends a DELETE to whatever URI it names, a namespace or a claim included (`/api/v1/namespaces/web`), so every `oc delete --raw` counts, in any position; `oc get --raw` stays allowed. kubectl reads a Service's remote port with Go's `strconv.Atoi`, which accepts a leading `+`, so the port-forward check of ADR 0028 §5 item 4 reads `15432:+5432` as 5432. argocd's release downloads keep their file names (`argocd-linux-amd64`, `argocd-darwin-arm64`, `argocd-windows-amd64.exe`), under which argocd runs its command-line client, so every argocd check also counts a program whose name starts with `argocd` followed by `-`, `_` or `.`.
- **Text that `xargs` or `parallel` pass on.** Piped `echo` or `printf` text, or a here-string, that `xargs` or GNU `parallel` read becomes the arguments of the command they run, as ADR 0028 §4 already reads it for `oc exec`, `oc rsh` and `oc debug`. The hook now reads it so for every command whose arguments the checks read: `oc`, `argocd`, `cargo`, `backend3-cli`, `sea-orm-cli`, `psql`, `pg_restore`, `mysql` and `mariadb`. So `echo confirm-deletion backend3 | xargs argocd app` and `echo pvc/data | xargs oc delete` are blocked, and so is `echo -n pvc/data | xargs oc delete`, whose `-n` is echo's option, not oc's namespace option. A command that `xargs -a` runs gets that text on stdin instead, and for any other program it stays data.
- **`argocd` as an option's value.** In `oc get application backend3 -n argocd -o jsonpath=...`, `argocd` is the value of the earlier oc's `-n`, upstream Argo CD's default namespace, or of `--context`, not a program. Item 3 does not count it as an argocd command, so reading the annotation there stays allowed, also in a namespace named like a download name (`-n argocd-system`). That holds only where the segment's first `oc` surely runs and only reads. It must stand where the program goes for sure: after nothing but assignments, runner words with no options of their own that run the next word (`sudo`, `env`, `nice`, `exec`, `command`, `xargs`, the shell keywords and the like) and `timeout` with a plain duration (`timeout 30 oc get ...`). After a runner's own options the word `oc` may be one of their values and `argocd` the program: GNU env runs `env -u oc -v argocd app patch ...` (`-u` unsets a variable named oc, `-v` is `--debug`), bash runs `exec -a oc -c argocd ...`, and sudo runs `sudo -u oc -n argocd ...` as the user oc. After `ssh` it is a host, and OpenSSH reads options again after the host, so `ssh oc -n argocd ...` runs argocd there. And every verb that oc may run in the readings above must be `get` or `describe`, since a verb that runs a program runs argocd in a pod (`oc run cli --image ... --command -- sudo -n argocd app patch ...`) and one reading may take for the verb a word that is an option's value in the other (`oc --field-manager get run ...` runs `oc run`). This only narrows an exception, so it errs towards blocking.

A resource argument with an empty type part (`oc delete ,`, `oc delete /x`, the `/dev/fd/63` that `oc delete <(...)` passes) names no kind. The hook used to stop with an error there, which blocked the command with a reason saying its input could not be read; kubectl refuses such an argument anyway.

Each block reason names ADR 0024 §4, ADR 0028 and this ADR, and says what was refused and what to do instead.

## Consequences

**Positive**

- The three paths that ADR 0028 left open are closed in the hook and, where a text rule can match them, in the deny rules: `redis-cli` run in a running pod through `oc exec`, `oc rsh` or `oc debug`, a finalizer or reclaim-policy patch through Argo CD, and Argo CD's deletion approval, through confirm-deletion and through the annotation itself.
- Each new check extends a rule the hook already has: the argocd subcommand finder, the patch rule and the in-cluster rule. The two readings of the port-forward check now rest on the maintainer's answer.
- The readings at the end of section 2 close those spellings for ADR 0028's checks too: `oc -p '<patch>' patch pvc data`, `oc --wait ns delete web`, a finalizer patch written with escapes, a JSON patch that replaces `/metadata`, `oc delete $'\x6e\x73' web`, `bash <(echo 'oc delete ns web')`, `oc delete --raw /api/v1/namespaces/web`, `oc port-forward svc/postgres 15432:+5432`, `./argocd-linux-amd64 app delete backend3`, `echo pvc/data | xargs oc delete`, `echo -n pvc/data | xargs oc delete`, `timeout 30 $(echo oc) delete ns web` and `"$(echo oc)" delete ns web` are blocked as well. Most of them are the website_k8s guardrails PR's readings, and that PR takes the rest from this hook (section 5), so both hooks read one rule set, apart from the one choice that section 5 leaves to that PR: how its patch decoder reads an escaped backslash.
- The website_k8s PR goes up once, with the final rules, for one human review.

**Negative and risks**

These replace ADR 0028's bullet on the three paths outside D69's answer; its other bullets hold. The answer to D110 (Context) covers parts of the bullets below on other Redis programs, a `redis-cli` in a pod that the agent starts, the annotation in a manifest and `argocd app patch` of an Application's own finalizers; until ADR 0036 and its follow-up PR apply it, they hold as written here ("Follow-up work").

- Running `redis-cli` in a pod, `redis-cli ping` and `INFO` included, changing a finalizer through Argo CD, additions included, approving a held deletion, and setting or removing the deletion-approved annotation are tasks for a human.
- Only `redis-cli` is recognised as a Redis client in the cluster. Another program that speaks the Redis protocol there, such as `redis-benchmark`, which can send any command, `valkey-cli` or `keydb-cli`, or a raw socket, is not. Blocking one needs another answer or an amending ADR first (ADR 0001 §6).
- A `redis-cli` in a pod that the agent starts itself (`oc run ... -- redis-cli`, `oc create job`, a Pod or Job manifest) is not blocked, unlike `psql`, whose target check catches a remote `-h` there. The answer names `oc exec`, `oc rsh` and `oc debug`, and `redis-cli` has no target check (section 2 item 4). Blocking it needs another answer or an amending ADR first (ADR 0001 §6).
- The annotation is matched by the word `deletion-approved`, so an `oc annotate` or `oc patch` with that word anywhere, whatever the key, and an argocd command that only prints such a key (`argocd app list --selector deletion-approved=yes`), are blocked too. So is a command in which an `argocd` word is only an argument before that word (`grep -rn argocd docs/deletion-approved.md`, `echo argocd deletion-approved`), as every argocd check has read since ADR 0028. D109 confirms this reading. An agent reads the key by piping argocd's output to `grep` or `jq`, or with `oc get`, and for text the block reason says to write it to a file and pass the file. The patch rule and the annotation rule decode escapes first, and also decode one after an escaped backslash (`\\u0061`), which errs towards blocking; website_k8s's hook reads `\\` as an escaped backslash (section 5).
- The annotation is checked only where an `oc annotate`, an `oc patch` or an argocd command names it, the routes that D105's answer names and the argocd commands that D109's answer confirms (section 2 item 3). A manifest that sets it is not checked when `oc apply`, `oc create` or `oc replace` reads it, even when its text is in the command as a heredoc or as piped `echo` text, and neither is one in a file, in another command's output or in an editor (`oc apply -f`, `oc edit`, `argocd app create -f`, `argocd app edit`), like the other file-based paths of ADR 0024 §4.
- Text that only the shell computes stays invisible to every check, the new ones included, as for the older ones: a variable's value (`--patch "$P"`), `printf` formats and `echo -e` escapes, brace expansion (`{a,b}`), globs and decoded output (`base64 -d`). The `echo` or `printf` text that a shell runs is read as written, and `$'...'` quoting is decoded (section 2). Only a reclaim policy whose value holds a shell expansion counts as not checkable (ADR 0028 §5 item 3). A substitution that fills in only part of the command name (`o$(echo c) delete ns web`, `"o$(echo c)" ...`), or a double-quoted one with double quotes of its own inside (`"$(echo "$(echo oc)")" delete ns web`), is not read either, like the other words that only the shell puts together. The hook also ends the output of each `echo` and `printf` with a line break, so output that bash prints on one line (`printf oc; echo ' delete ns web'`, or an `echo -n` before another `echo`) is read as two lines.
- Text that `xargs` or GNU `parallel` read from a heredoc, directly or through `cat` (`xargs oc <<'EOF'`, `parallel oc delete <<'EOF'`, `cat <<'EOF' | xargs oc`), is not read as the arguments of the command they run, although a here-string or piped `echo` text is (`xargs oc <<< 'delete ns web'`). Neither is a here-string that `cat` passes on through a pipe, to `xargs` or to the stdin of `oc exec` (`cat <<< 'delete ns web' | xargs oc`, `cat <<< 'redis-cli flushall' | oc exec -i redis-0 -- sh`), although a heredoc that `cat` passes to `oc exec` is. ADR 0028's hook does not read them either (`cat <<< 'psql -c x' | oc exec -i pg-0 -- sh`). They are spellings of the accepted rules, not new paths, so reading them is a fix of those rules (ADR 0001 §5), which the follow-up PR of D110's answer takes up ("Follow-up work").
- oc's verb and its words are read in every way oc may read them (section 2), and every reading counts, so a command that oc would refuse can be blocked, as ADR 0028 says for argocd: `oc --new-option get delete pvc`, for a resource type named `delete`. Text that `xargs -0` or `xargs -d` passes as one argument is read word by word, which errs towards blocking too.
- Some readings of section 2 block more than the data-loss paths: every `oc delete --raw`, whatever its URI names; every `$patch: replace`, `$patch: delete` and `$retainKeys`, and every key `path` set to `""` or `/metadata`, or to a YAML block scalar or alias, or to a tag whose value starts on the next line, wherever it stands in a patch, its value read with its spaces and tabs dropped too (`"/meta data"`); JSON's `\/` in an `oc patch` JSON patch, which kubectl refuses anyway; a substitution after a runner word (`sudo`, `timeout`), which counts as one in the command name's place wherever it stands, so its `echo` or `printf` output is also read as commands; and `echo` or `printf` text in a process substitution that a shell gets, also as an argument of a script (`bash run.sh <(echo ...)`). A program whose name starts with `argocd-`, `argocd_` or `argocd.` counts as argocd, so Argo CD's component names (`argocd-server`) count too, and so does a word such as an Application named `argocd-apps` in an oc command that names the deletion-approved annotation after it, unless it is the value of an oc option. That exception holds only for an `oc get` or `oc describe` that surely runs (section 2), so an `argocd` word stays an argocd command after an oc with any other verb, or behind a runner's own options, ssh or a number other than `timeout`'s duration (`sudo -u root oc get application backend3 -n argocd -o jsonpath=...`). These are tasks for a human, or a reason to rephrase the command, like the other false positives of ADR 0028.
- Neither hook checks these routes, which website_k8s's `CLAUDE.md` lists as well: an `oc replace`, `oc apply` or `oc edit` that drops finalizers or replaces a whole object (`oc get pvc data -o json | jq 'del(.metadata.finalizers)' | oc replace -f -`), and `oc replace --raw`, the counterpart of the `oc delete --raw` that section 2 blocks; `argocd app sync --prune` and `argocd app set --auto-prune`, which delete what the manifests no longer hold; an ssh tunnel to a database (`ssh -L 15432:<db>:5432 <host>`), which makes it answer on localhost as a port-forward does; file commands in a pod (`oc exec <pod> -- rm -rf /var/lib/postgresql/data`); commands that an interpreter runs (`python3 -c 'import os; os.system(...)'`); and output redirected into a process substitution (`echo '...' > >(bash)`), the reverse of the `bash <(echo '...')` that section 2 reads. No answer covers them, so blocking one needs another answer or an amending ADR first (ADR 0001 §6).
- argocd runs its command-line client under any file name that is not one of its components' names (`cmd/main.go`), so a copy renamed to something other than a download name (`ad`, `cd-cli`) is not recognised, like a client named by a variable.
- `argocd app patch` that changes the finalizers of the Application itself, by naming them or by replacing its metadata, is outside D105's answer, which names patch-resource, so the hook does not block it. Deleting the Application stays blocked (ADR 0028 §5 item 2).
- As ADR 0028 says, and D106 confirms: the port-forward check knows databases by their ports. A database served on another port is not recognised, a non-database service on one of those ports is blocked, and an engine the clusters do not run needs an amending ADR.
- website_k8s stays on its older guardrails until its human-reviewed PR merges.

| Count only argocd's exact release names (`argocd-<os>-<arch>`) | not offered; considered while writing this ADR | The website_k8s hook counts every name that starts with `argocd` and a separator, and both hooks read one rule set. The other names this covers are Argo CD's own components, which an agent does not run. |
| Treat every `$'...'` part as text that cannot be checked, and block it | not offered; considered while writing this ADR | It would block `printf` formats, search patterns and commit messages written with `$'...'`, which decoding reads as bash does. |
| Read a heredoc's receiving line and a command part only as the lexer reads them, without the quote-stripped reading | not offered; considered while writing this ADR | The quote-stripped reading is the one ADR 0028 built and its tests pin, and it errs towards blocking. Keeping it next to the decoded one means that no spelling which ADR 0028's hook blocked passes now. |
| Put the output of a substitution after a runner's own words in its place, as in the command name's own place | not offered; considered while writing this ADR | The substitution may be a runner's argument or the command's, and the hook reads `echo` and `printf` output without applying their options or formats, so `sudo oc port-forward svc/postgres $(printf 54%s 32)` would pass for a port that is not a database's. |
| Read the values of every YAML form in a patch as go-yaml does | not offered; considered while writing this ADR | It needs a YAML parser in the hook. Agents write patches as JSON or plain YAML, so the forms whose value the hook does not read, block scalars and aliases, count as whole-metadata patches instead. |
| Widen the port-forward check to more engines' ports, to pod and service names, or both | third decision register D106, options 2 to 4 | The maintainer confirmed the readings as built. Every database Service in website_k8s is already blocked by its port, and reading names would block `svc/postgres` 9187, backend3's PostgreSQL metrics. |
