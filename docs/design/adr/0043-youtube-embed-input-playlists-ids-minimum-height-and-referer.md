# 0043. YouTube embed input, playlists, ids, minimum height and Referer

- Status: Accepted (2026-11-01)
- Decision questions: none: records the maintainer's answers of 2026-11-01 to items D128-D138 of the third decision register (research: DECISIONS R28), which settle eleven rules for YouTube embeds that [ADR 0013](0013-rich-text-editor-and-html-sanitiser.md) and [editor.md](../editor.md) leave open or state differently from what YouTube writes. It amends four parts of ADR 0013: the YouTube canonical shape of §1, the `POLICY_VERSION` sentence of §1, the YoutubeEmbed row of §2 and follow-up 7.

## Context

[ADR 0013](0013-rich-text-editor-and-html-sanitiser.md) decides YouTube embeds in four places that this ADR touches:

| Part of ADR 0013 | What it says |
|---|---|
| §1, canonical shapes, the YouTube row | "`<p data-youtube-video=""><iframe src="https://www.youtube-nocookie.com/embed/<id>" …>` with a responsive style (`aspect-ratio: 16 / 9; height: auto; max-width: 640px; width: 100%`), one fixed `allow` value, `allowfullscreen` and `referrerpolicy="strict-origin-when-cross-origin"`. Only `start` and `list` survive in the query." |
| §1, content-v1 as data | "`POLICY_VERSION` is `"content-v1"`." |

| Consequences, follow-up 7 | "Renderer fixes are recommended, never required, and belong to other repositories ([editor.md](../editor.md) §15)." |

A research note of 2026-10-25 recorded what YouTube's Share dialog, its share links and the player's context menu write, in desktop Chrome and signed out, and read YouTube's developer and Help pages (research: youtube-embed §0). It is the YouTube half of the snippets that D25 asked for ("Provide both snippets", research: DECISIONS R9). Its 28 fixtures are inputs for the editor's tests. Of its 18 live captures, 13 kept no copy (research: youtube-embed §0, §11). It found eleven conflicts with the design (research: youtube-embed design conflicts):

1. **The embed code probably arrives as plain text.** Share > Embed's Copy button and the player menu's "Copy embed code" copy from a text box with `document.execCommand('copy')`. The research infers, without a recorder capture, that the clipboard then holds only `text/plain`. With no `text/html`, prosemirror-view 1.42.7 takes its text path: `transformPastedHTML` never runs, so parse rule 60 never sees the code, and it lands in the body as literal `<iframe …>` text (research: youtube-embed §2.4). Staff have pasted that code since 2021-12: bare YouTube iframes in 13 posts **[500]** (ADR 0013 Context), and v1 has no HTML view.
2. **Playlists.** Share > Embed on a playlist writes `/embed/videoseries?list=<id>`. YouTube's developer docs give only `/embed?listType=playlist&list=PL…`. editor.md names neither form. `videoseries` passes today only because its 11 letters fit both id rules, with or without `list`, and the documented form fails the path rule (research: youtube-embed §5.3). None of the 19 legacy YouTube iframes is a playlist (research: gap-06 §4.5).
3. **Links on the bare host.** The Shorts player's Share sheet, which has no Embed, writes `https://youtube.com/shorts/<id>?si=…`, and a playlist page writes `https://youtube.com/playlist?list=<id>&si=…`, both on the bare host `youtube.com` (research: youtube-embed §4). The lone-URL paste rule of editor.md §4.3 row 9 names neither the bare host nor `/playlist`.
4. **Start times in links.** The Share panel's "Start at" box and the player menu's "Copy video URL at current time" write `t=<seconds>` (`t=90`, `?t=97`, `&t=8` after `list`). YouTube also honoured `t=90s` on a watch URL typed by hand; the `1m30s` form was not checked (research: youtube-embed §4, §5.2). editor.md §3.7 drops every query parameter other than `start` and `list`.
5. **Two id rules.** The server's `iframe[src]` rule, built and merged, keeps a video id of one or more `[A-Za-z0-9_-]`. The node's `videoId`, not built yet, takes 6 to 20. YouTube's IFrame API reference rejects "a video ID that does not have 11 characters" (onError 2). The 19 YouTube ids of the harvest **[500]** and every video id of the 28 fixtures have 11 (research: youtube-embed §1 item 10; research: gap-06 §4.5). An id that the server keeps but the node refuses disappears when the editor opens the body, and `J(c) == c` fails ([editor.md](../editor.md) §6).
6. **Player size.** YouTube's player docs: "Embedded players must have a viewport that is at least 200px by 200px", and they recommend at least 480 × 270 for a 16:9 player. content-v1 locks `width: 100%` and `aspect-ratio: 16 / 9` on the iframe, so in a column narrower than about 356 px the player is less than 200 px tall: 343 × 193 in a 343 px phone column (research: youtube-embed §6).
7. **Options dropped without a word.** Unchecking "Show player controls." in Share > Embed writes `controls=0`, and YouTube documents `end`, `autoplay` and `loop` with `playlist`. The editor drops all of them, and neither the paste report nor any notice says so (research: youtube-embed §7). None of the 19 legacy iframes carries one.
8. **Titles.** Share > Embed writes the generic English title "YouTube video player". The player menu writes the video's real title. A URL insert and the 6 oEmbed embeds of rule N1 have no title. A frame title "should concisely describe the embedded content" (MDN, `<iframe>`). editor.md keeps whatever title arrives and gives no default (research: youtube-embed §6).
9. **http.** YouTube's own Help article prints an embed whose `src` is `http://www.youtube.com/embed/UkWd0azv3fQ?start=90`. backend3 stores YouTube embeds only on https (research: youtube-embed §5.2, §9).
10. **The Referer.** YouTube's Required Minimum Functionality requires the HTTP Referer from embedded players and recommends `strict-origin-when-cross-origin`. Without a Referer, playback is blocked with error 153, which entered the IFrame API reference on 2025-07-09 (research: youtube-embed §6). content-v1 stores that value on every iframe ([editor.md](../editor.md) §3.2), and under the Fetch standard (§4.1) the page's own Referrer-Policy applies only when the element has no such attribute. website_frontend2's DOMPurify strips the attribute (ADR 0013 Context), and editor.md §11.4 and §15.2 count that only as a fullscreen and fidelity issue.
11. **Capture and licence.** editor.md §16 item 2 and ADR 0013 follow-up 2 track only Padlet's snippet; only the "Also" line of editor.md §13.2 asks for YouTube's code. The recorder JSON with the clipboard types, which item 1 rests on, does not exist for YouTube. editor.md §13.1 has no fixture row for markup that a third-party service generates, and whether such fixtures need a `THIRD_PARTY.md` row was open (research: youtube-embed §11 items 1 and 6).

**Versioning.** Under [editor.md](../editor.md) §3, a change to content-v1 bumps `POLICY_VERSION` and ships with a `content_normalize` run. Two earlier changes were made in place, because nothing was stored yet: R11's hardening, confirmed by D87 (research: DECISIONS R15), and the nested-link rule of D112 (research: DECISIONS R21, [ADR 0037](0037-nested-links-unwrapped-by-the-sanitiser-s-structural-pass.md)). No body is stored before the `content-write-service` slice, and production holds none before the cut-over import (research: third decision register D133).

ADR 0013 §1 and §2 decide the YouTube shape and the editor's inputs, and its follow-up 7 the renderers, so changing them changes an Accepted decision. Under §6 of [ADR 0001](0001-record-architecture-decisions.md) only a new ADR that quotes the maintainer's answer does that. The maintainer answered all eleven items on 2026-11-01 (research: DECISIONS R28), each with the recommended option. ## Decision

### 2. What the editor turns into a YouTube embed (D128, D130, D131, D136)

YoutubeEmbed has one reader for every YouTube input: its iframe parse rules, the lone-URL paste rule, the insert dialog and the plain-text route below. The reader reads an iframe's `src` only through a DOM parse, so `&amp;` is decoded. Whatever it reads, the node writes the canonical shape of section 3.

- **Embed code as plain text (D128).** When a paste carries no `text/html` and its trimmed `text/plain` is exactly one `<iframe …></iframe>` element, the reader parses it in an inert `DOMParser` document, and it goes through the schema's parse rules as an HTML paste does (rule 60). Anything else stays text, including an iframe from a host outside [editor.md](../editor.md) §3.6, and Padlet's snippet, which is wrapped in a div. The paste hook is a `clipboardTextParser`. ProseMirror calls it only on its text path, so an HTML paste still takes rule 60, and nothing changes if the recorder run finds that YouTube writes HTML after all. The hook declines when ProseMirror flags a plain-text paste (Shift held, as in Ctrl+Shift+V), so that paste keeps the code as text. The insert dialog takes the same code as well as a URL. content-v1, the sanitiser and the stored bytes do not change.
- **Lone URLs (D130).** The paste rule and the insert dialog accept exactly this list: `youtu.be/<id>`; `/watch?v=<id>`, `/shorts/<id>` and `/playlist?list=<id>` on `www.youtube.com`, the bare `youtube.com`, `m.youtube.com` and `music.youtube.com`; `/embed/…` on `www.youtube.com` and `www.youtube-nocookie.com`. A Short's link becomes the standard `/embed/<id>` player at 16:9, with the Short pillarboxed, as YouTube's own Embed code gives a Short. A `/playlist` link becomes `/embed/videoseries?list=<id>` (section 3). `m.` and `music.` stay uncaptured, because the capture was desktop only.
- **Start times (D131).** On a `youtu.be`, watch or shorts link, a `t` that matches `^\d+s?$` becomes `start`. If the link also has `start`, `start` wins. `t=0` gives no start, as the Share panel writes no `t` at 0:00. An `/embed/` src reads only `start`, which is what YouTube writes there. Any other spelling of `t`, such as `1m30s`, is dropped like `si`.
- **http (D136).** The parse rules, the paste rule and the insert dialog accept `http` on the same hosts and paths. The node writes its usual `https://www.youtube-nocookie.com/embed/<id>` address, as for every input, so no http address reaches the server. There is no message: the embed plays the same video from the same start. The server's https-only rule, `policy.json` and the sanitiser do not change; like `youtu.be` and watch URLs, the upgrade is an editor-side input mapping.

### 3. The stored shape (D129, D132, D133)

A single video and a whole playlist are stored as:

```html
<p data-youtube-video=""><iframe src="https://www.youtube-nocookie.com/embed/dQw4w9WgXcQ?start=90" width="640" height="360" title="Videó" style="aspect-ratio: 16 / 9; height: auto; max-width: 640px; min-height: 200px; width: 100%" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" allowfullscreen="" referrerpolicy="strict-origin-when-cross-origin"></iframe></p>
<p data-youtube-video=""><iframe src="https://www.youtube-nocookie.com/embed/videoseries?list=PLMOZDTW7ZvXM" width="640" height="360" title="Videó" style="aspect-ratio: 16 / 9; height: auto; max-width: 640px; min-height: 200px; width: 100%" allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share" allowfullscreen="" referrerpolicy="strict-origin-when-cross-origin"></iframe></p>
```

The ids are those of the research fixtures: a public video of an official artist channel, and a public playlist of YouTube's own channel (research: youtube-embed §10.4).

- **The video id (D132).** `[A-Za-z0-9_-]{11}`, exactly 11 characters, on the server and in the node. The Rust policy gives the YouTube provider its own id length, and `policy.json` exports it beside the shared id alphabet, so the node reads the same rule and the two sides cannot drift apart ([editor.md](../editor.md) §3.9). An id of any other length is refused at insert and URL paste, on an admin write (`422 embed_rejected`, whose message says only that YouTube and Padlet embeds may be used, not that the id is wrong) and at import, which reports the embed. Every id counted so far passes. Padlet keys and `list` values keep `[A-Za-z0-9_-]+`. If YouTube ever issues ids of another length, those videos cannot be embedded until a PR widens the rule; after go-live that is a policy change with a `POLICY_VERSION` bump.
- **Playlists (D129).** A YouTube path is `/embed/<videoId>`, or the literal `/embed/videoseries` only together with `list`, which stores a whole playlist. The start-then-list query rule does not change. `embed_src` refuses `videoseries` without `list`, `policy.json`'s `urls.embed` carries the same rule for the admin, and the node's `videoId` takes `videoseries` only with `list`. The reader of section 2 rewrites `/embed?listType=playlist&list=<id>` to `/embed/videoseries?list=<id>` and keeps the list as given. The result equals what a pasted Share > Embed playlist is stored as once `si` is dropped, so the rewrite adds no second stored shape. `listType=user_uploads`, whose list is a user name, and `listType=search`, a 4xx since 2020-11-15, get a new `editor.*` message. The server never accepts `listType`.
- **Minimum height (D133).** The canonical style becomes `aspect-ratio: 16 / 9; height: auto; max-width: 640px; min-height: 200px; width: 100%`. Columns 356 px and wider, desktop included, look exactly as before. In a narrower column the player keeps the column width and is 200 px tall, a little taller than 16:9 (343 × 200 instead of 343 × 193). It always stays inside its column. YouTube should letterbox the video inside the box, but that was not tested. The CSS grammar accepts `min-height` only at `200px`, and only on `iframe`; a Padlet iframe could therefore carry it too, but the Padlet shape does not change.

### 4. What the editor drops, says and writes as the title (D134, D135)

- **Dropped options and the notice (D134).** content-v1, the server rule and ADR 0013 do not change: only `start` and `list` are stored. When `controls=0`, `end`, `autoplay=1`, `loop` or `playlist` was dropped, the editor shows one Hungarian notice per paste or insert, for example „A YouTube-videó néhány beállítása (például a vezérlők elrejtése vagy az automatikus lejátszás) nem marad meg, a videó a szokásos lejátszóval jelenik meg.” (one `editor.*` string). It shows on an HTML paste, on a URL pasted on its own, under the insert dialog's URL field, and on the plain-text route of section 2. The paste report gets an entry for the drops (`dropped.embedParams`, [editor.md](../editor.md) §5.2 step 12). Tracking, deprecated and other parameters (`si`, `pp`, `feature`, `rel`, `showinfo` and the like) are still dropped silently.
- **Titles (D135).** A missing or blank title, or exactly "YouTube video player" after trimming, becomes „Videó”. Any other title is kept as written. The insert dialog has a title field that starts as „Videó” and that staff can edit; the lone-URL paste rule writes „Videó”; the paste filter applies the rule to pasted YouTube iframes, and so does the plain-text route; the import gives the 6 N1 embeds „Videó”, and N2 replaces only a missing or generic title. On load the node keeps whatever stored title it finds, or none, so the fixed points P-fix and J hold. editor.md §3 is not edited, because its example already shows „Videó”, so content-v1, `POLICY_VERSION`, the sanitiser and ADR 0013 stay as they are, and an API write can still store any title, or none. „Videó” is still generic: it names the kind of frame in the site's language, not the video. Only YouTube's English generic title is known; a Hungarian UI's, if it differs, is kept like a real title until a capture adds it to the rule.

### 5. The Referer (D137)

- **The requirement.** Any public renderer that shows backend3's stored content must keep the iframe's `referrerpolicy`. What YouTube receives is decided by that attribute, not by the page's Referrer-Policy (Fetch §4.1), so the rule holds whatever header a host sends later. This replaces ADR 0013 follow-up 7 for this one fix; every other renderer fix stays recommended, never required.
- **The Angular site** keeps the attribute: it inserts the body as trusted HTML (ADR 0013 Context), and its REST PRs leave the page renderer alone. No other repository changes.
- **website_frontend2** strips the attribute with DOMPurify. Allowing `referrerpolicy` on iframes is required before frontend2 shows backend3 content; frontend2 stays out of scope until then (research: DECISIONS 31; [ADR 0026](0026-backend2-unchanged-and-running-until-decommissioning.md)).
- **The check.** [cutover.md](../cutover.md) §7 adds a row to G9's page list: an imported post with a YouTube embed plays in a browser, with no error 153. The dress rehearsal and the window run it by hand, on the page itself: an embed URL opened on its own in the address bar sends no Referer and shows error 153 anyway (research: youtube-embed §6).

### 6. Fixtures and the recorder run (D138)

- **The open item.** [editor.md](../editor.md) §16 item 2 becomes "Padlet's and YouTube's current embed code". It closes when Padlet's snippet and YouTube's recorder JSON are committed.
- **The run.** The maintainer or the staff paste three copies into the recorder in Chrome, Edge and Firefox: Share > Embed > Copy, Share > Copy and the player menu's "Copy embed code". The same run re-takes the 13 values that have no retained evidence (research: youtube-embed §11 item 1). It needs no Office, so it can be part of the clipboard-captures session or run on its own. Its JSON shows which clipboard path YouTube's code takes. Section 2 works on either path.
- **Scrubbing.** The recorder scrubs only profile-folder names, so before commit each live `si` is replaced by hand with an invented token (public-safety rule 3 of [ADR 0001](0001-record-architecture-decisions.md) §8).
- **Licences.** [editor.md](../editor.md) §13.1 gains a fixture-source row for output that a third-party service generates and the project captures: the markup is YouTube's, not the project's, so the AGPL "Own captures" row cannot cover it. `THIRD_PARTY.md` gets one row for the YouTube fixtures: YouTube as the generator, the capture dates, "not under the repository licence", and modified (`si` replaced). Padlet's snippet gets the same kind of row when it arrives. `editor-images-embeds` adds the rows in the PR that adds the fixtures, as [ADR 0012](0012-delivery-review-commits-and-licensing.md) §4 requires for vendored code.

### 7. Versioning

- **The bump.** The new locked declaration of section 3 is a content-v1 policy change ([editor.md](../editor.md) §3), so `editor-images-embeds` bumps `POLICY_VERSION` in `policy.rs` and `policy.ts`, from `"content-v1"` to `"content-v2"`, the name the second register's D87 gave the next version (research: DECISIONS R15). D129's and D132's rule changes land in the same PR and share the bump (research: third decision register D133).
- **No rewrite.** Nothing is stored before `content-write-service`, so no body is rewritten and `content_normalize` has nothing to do. The cut-over import writes the new style into production (`normaliser-embeds`); after that, any change to the style would rewrite every production body that has a YouTube embed, with a revision for each.
- **Until the code lands**, the code enforces the earlier rules, and the tables of editor.md §3 already show the rules of this ADR.

## Consequences

**Positive**

- Staff keep the habit they have had since 2021-12, pasting YouTube's embed code, in the body and in the dialog, whatever clipboard type YouTube writes; an HTML paste behaves as before.
- Every link that YouTube's Share button and player menu write becomes a player: Shorts from the Shorts player, playlists, links with a start time, and YouTube's own http example.
- One id rule on both sides, exported once: `J(c) == c` holds for every id the server keeps, and a mistyped id is caught when it is inserted, instead of readers seeing the player's error.
- Playlists are stored by rule, not by accident, in one shape.
- Every player meets YouTube's 200 × 200 px minimum in any column at least 200 px wide, and nothing changes from 356 px up. It costs one locked declaration and no rewritten body, because nothing is stored yet.
- Nothing staff chose in YouTube's dialog disappears without a word.
- Every new and imported embed has a label in the site's language.
- The Referer rule holds whatever header a host sends, and the go/no-go check catches an embed failure on the renderer that actually ships.
- The evidence D128 rests on gets a tracked run, and the fixtures' licence status is indexed where the repository indexes licences.

**Negative**

- The plain-text route converts only one iframe from an allowed host. Padlet's snippet and anything else pasted as text stay text.
- If YouTube ever issues ids of another length, those videos cannot be embedded until a PR widens the rule.
- In a column narrower than 356 px the player is a little taller than 16:9, and YouTube's letterboxing there is untested.
- `controls=0`, `end`, `autoplay` and `loop` cannot be kept; staff are told, not offered them.
- „Videó” is generic, and an API write can still store any title, or none.
- frontend2 cannot show backend3 content until its renderer keeps `referrerpolicy`.
- One more manual go/no-go check, in the dress rehearsal and in the window.
- The bump touches every test, vector and fixture that pins the YouTube style, and after the cut-over import any change to that style rewrites every production body that has a YouTube embed.
- `m.` and `music.` links stay uncaptured, the `1m30s` form of `t` is dropped, and whether `/embed/videoseries` plays on the nocookie host inside a page is untested (research: youtube-embed §11 item 4).

**What must be true in code and tests**

- **Server.** `embed_src` refuses a YouTube id that is not 11 characters, `videoseries` without `list`, and every `listType`. The server tests and regression fixtures that use `x`, `abc`, `a`, `VIDEOID` or `a-b_C9` as YouTube ids use 11-character ids. The CSS grammar accepts `min-height` only at `200px` and only on `iframe`, `css/vectors.rs` has min-height cases, and `policy.json`, `css-vectors.jsonl` and the `css_vectors` snapshot are regenerated. The YouTube style with `min-height: 200px` is pinned in the `sanitize.rs`, `css/mod.rs` and `css/canonical.rs` tests and in the canonical-shapes fixture. `POLICY_VERSION` is `"content-v2"` in `policy.rs` and `policy.ts`.
- **Editor (L1).** The research's dialog fixtures, fed as text, become embeds. The `t` fixtures give `start=90` (share link), `start=97` (player menu), `start=8&list=PLMOZDTW7ZvXM` (player menu inside a playlist) and `start=90` (the typed `t=90s` watch URL). `youtube-help-start-http.html` gives `https://www.youtube-nocookie.com/embed/UkWd0azv3fQ?start=90`. Both captured share links, the Short and the playlist, embed. `listType=playlist` maps to `videoseries`, and `user_uploads` and `search` show the message. The title rule holds on each route. The notice shows on each route with the controls-off, all-options, playlist-all-options, start-end, loop and autoplay fixtures, and not for `si` alone.
- **Paste (L3).** A text-only clipboard that holds YouTube's embed code becomes an embed in Chromium and Firefox; with Shift held it stays text; an HTML clipboard with the same iframe still takes rule 60.
- **Import.** N1 and N2 write the new style and the title rule, and every imported body is a fixed point (`J(c) == c`, data-migration.md N9 and V13).

## Alternatives considered

The chosen option of each item is the rule of sections 2 to 6 (research: DECISIONS R28). The others:

| Option | Source | Why not |
|---|---|---|
| Take the embed code only in the insert dialog | third decision register D128 | Leaves the most likely paste, into the body, as visible code with no warning. |
| Keep the design: HTML pastes and URLs only | third decision register D128 | Makes answer 15's bare iframes depend on a clipboard that YouTube probably never writes. |
| Decide after a recorder capture of YouTube's Copy | third decision register D128 | Waves 9 and 10 would be built without the route while the capture had no owner. The chosen route is right whatever the capture shows. |
| Name videoseries, require list, and refuse every listType URL | third decision register D129 | Turns the only playlist form in YouTube's docs into an error. |
| Leave it as now: videoseries passes as an ordinary video id | third decision register D129 | Playlists stay accepted only while the id rule happens to match an 11-letter word, and `/embed/videoseries` without `list`, a shape nobody has tested, is stored too. |
| Refuse whole-playlist embeds | third decision register D129 | Costs nothing in legacy content, but takes away a form that YouTube's Share dialog offers for every playlist. |
| Add the bare host only | third decision register D130 | Leaves playlist share links as plain text, although D129 gives them a stored form. |
| Neither the bare host nor /playlist | third decision register D130 | For every Short shared from the Shorts player, staff would have to copy the address bar or open a second page. |
| Also read the h/m/s form of `t` (`1m30s`) | third decision register D131 | No evidence that YouTube writes it. If a later check finds it, it is an editor-only change, because nothing stored depends on how the input was spelled. |
| Keep dropping `t` | third decision register D131 | A staff member who sets 1:30 and pastes the link means 1:30; dropping it throws that choice away without telling them. |
| 6 to 20 characters on both sides | third decision register D132 | Stores ids that YouTube rejects (onError 2), so readers see the player's error. |
| Any length on both sides, as merged | third decision register D132 | Checks no length at all: a mistyped id is published as a broken embed. |
| Any length, and 11 only for new ids in the dialog and the URL paste rule | third decision register D132 | Keeps two rules, and checks only the editor's own dialogs. |
| Accept and document the size gap | third decision register D133 | Leaves every embed in a narrow phone column below a "must" in YouTube's docs, with an untested effect; adding the minimum after the cut-over import would rewrite every production body that has a YouTube embed. |
| A locked `min-width: 356px` | third decision register D133 | The player sticks out of a column narrower than 356 px (13 px in a 343 px column), which brings back the phone overflow that the responsive player removed. |
| Drop the options silently, as designed | third decision register D134 | Leaves the staff member guessing why the saved player differs from YouTube's preview. |
| Store some of the options | third decision register D134 | Needs a policy change on both sides and an amending ADR, and works against readers: `controls=0` hides the controls from every reader, `autoplay=1` starts YouTube's data collection before anyone plays the video, and `loop` needs a second id list. `end`, the one with a plain use, was not seen written by any YouTube tool; storing it stays possible later. |
| Default "Videó", enforced by the server | third decision register D135 | Adds a policy bump, an amending ADR and sanitiser work only to cover API writes from outside the editor. |
| Require a real title, like image alt text | third decision register D135 | Every insert then needs typing, and imported posts are blocked until someone adds the titles. It can still follow later as its own change. |
| Keep titles as they come | third decision register D135 | Leaves URL inserts and the N1 embeds with no label at all. |
| Refuse an http address, with a message | third decision register D136 | Makes the staff member fix the address by hand, for an embed the editor can rebuild from its id as it already does for every other input. |
| Upgrade http in the editor and on the server | third decision register D136 | Changes merged server code for an input that neither the editor nor any recorded legacy body produces. |
| Header requirement: every public site sends `strict-origin-when-cross-origin` | third decision register D137 | The page header does not decide what YouTube receives while the stored attribute is kept. It needs a human-reviewed PR in another repository before the cut-over, and every later host must remember it. |
| Both the renderer requirement and the header | third decision register D137 | The header adds the cost of the previous row to a rule that the attribute already makes hold. |
| Document it only | third decision register D137 | A later port that misses the paragraph, on a host that sends `no-referrer` or `same-origin`, would break every embed with nothing to catch it. |
| Recorder run, with the provenance file only | third decision register D138 | The markup is YouTube's, so the AGPL "Own captures" row cannot cover it, and with a provenance file alone `THIRD_PARTY.md` says nothing about these files. |
| No recorder run, with a `THIRD_PARTY.md` row | third decision register D138 | The recorder JSON is what shows the clipboard types D128 rests on, and the same run backs 13 values that have no kept evidence. |
| No recorder run, with the provenance file only | third decision register D138 | Both reasons above. |
