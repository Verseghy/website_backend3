# 0041. Budapest-midnight parity and a two-sided tz-data procedure

- Status: Accepted (2026-11-01)
- Decision questions: none: records the maintainer's answer of 2026-10-25 to the second decision register's item D96 (research: DECISIONS R15 (D96)), which settles how the tz-data procedure covers PostgreSQL's tz data as well as backend3's, and the answers of 2026-11-01 to the third register's items D122 to D124 (research: DECISIONS R25), which settle what writing the test left open: the calendar days after the end of chrono-tz's Budapest table, the production step of section 3, and how backend3 moves the stored values of a day whose midnight moves. It amends three parts of [ADR 0010](0010-all-instants-stored-as-timestamptz.md), which records Q9: point 2 (the days that the conversion module refuses), the tz-data procedure in its Consequences (the first "Negative" item) and its "What must be true in code and tests".

## Context

[ADR 0010](0010-all-instants-stored-as-timestamptz.md) point 2 stores a calendar day, such as `posts.date` or `canteen_days.date`, as the `timestamptz` of its Europe/Budapest midnight, and two tz databases look at that instant:

| Side | What it does with the instant | Its tz data | How the tz data changes |
|---|---|---|---|
| backend3 | `src/domain/budapest.rs` computes it (`date_to_midnight`) and reads it back (`midnight_to_date`), the one conversion module of point 5 | compiled into chrono-tz, pinned exactly (`chrono-tz = "=0.10.4"` in `Cargo.toml`): 2025b, recorded in `budapest::TZ_DATA_VERSION` and compared with chrono-tz's by a unit test | only through a backend3 PR. Dependabot proposes the patch releases of chrono-tz 0.10, and its semver-major rule keeps a new 0.x line out, so that line arrives only as a deliberate PR (`.github/dependabot.yml`) |
| PostgreSQL | the check of point 2, `CHECK ((date AT TIME ZONE 'Europe/Budapest')::time = time '00:00')`, refuses any other instant (ADR 0018 §1.3); SQL derives the day with `(date AT TIME ZONE 'Europe/Budapest')::date`, for example in the canteen days' unique index (ADR 0018 §4.1) and the archive's grouping (point 10) | the image's own: the official `postgres` image builds PostgreSQL with `--with-system-tzdata=/usr/share/zoneinfo` and so reads the Debian `tzdata` package of the image, 2026c in compose.yaml's `postgres:18.6` (checked with `pg_config --configure` and the first line of `/usr/share/zoneinfo/tzdata.zi` in that image) | with the image. compose.yaml, which CI and the local tests use, pins the tag and the digest and is bumped by hand (`AGENTS.md`, "Commands"). Production names the tag only, and Argo CD Image Updater opens a website_k8s PR for each new 18.x tag (website_k8s@f0286dc:verseghy-website/postgres/kustomization.yaml, verseghy-website/image-updater/imageupdater.yaml) |

What depends on the two agreeing:

- **Writes.** backend3 writes the instant from `date_to_midnight`. The check refuses it unless PostgreSQL also sees a Budapest 00:00:00 there, so the write fails.
- **Reads.** backend3 reads a stored value with `midnight_to_date`, which reports any instant that it does not see as a midnight as a defect (a server error), so a value that PostgreSQL let in may not read back.
- **SQL.** An index or a grouping on `(date AT TIME ZONE 'Europe/Budapest')::date` takes the day from PostgreSQL's tz data. PostgreSQL treats `AT TIME ZONE` with a named zone as immutable (`timezone(text, timestamp with time zone)` has `provolatile = 'i'` on PostgreSQL 18.6), so an index entry keeps the day computed with the tz data in force when its row was written.

What the two sides hold today:

1. A reviewer compared, for every day from 1890 to 2200, which days have no Budapest midnight or two under each side's tz data, and the lists matched (research: second decision register D96).
2. The test of section 2 compares the midnights themselves. They are the same on every day from 0001-01-01 to 2099-12-31, and the days with none or two are the eleven between 1916 and 1983 that ADR 0010 point 2 describes.
3. From 2100 on they differ. chrono-tz turns the tz data's rules into a table of offset changes when it is built, and for Budapest that table ends with the change of 2099-10-25 at 01:00 UTC (chrono-tz@0.10.4:src/prebuilt/timezones.rs); chrono-tz keeps winter time for every later instant. PostgreSQL applies the rules at run time and goes on changing the clocks: on PostgreSQL 18.6 with tz data 2026c, `2100-06-30T22:00:00Z` is 2100-07-01 00:00:00 in Budapest. So from 2100 on the midnight of each summer day, from the day after the spring change to the autumn change day, is an hour later in backend3 than in PostgreSQL, and the check refuses backend3's (217 days in 2100). The register noted this as "chrono-tz lists Budapest's clock changes only through 2099"; the reviewer's lists match there because no day has none or two midnights on either side.

ADR 0010's tz-data procedure names only backend3's side: a chrono-tz bump PR states its tz data version, and before it merges the operator compares the future events' wall times with the read-only task `events_tz_report`. That task does not exist yet; the `events-import` slice adds it, and no event is stored before then.

ADR 0010 states its procedure and its tests, so adding the PostgreSQL side changes an Accepted decision, which under §6 of [ADR 0001](0001-record-architecture-decisions.md) only a new ADR that quotes the maintainer's answer does. The maintainer answered on 2026-10-25 (research: DECISIONS R15), with the recommended option. The register's question, the answer, and the consequence it gave for that option (research: second decision register D96):

- **D96**, "posts.date and canteen_days.date carry a CHECK that each value is a Budapest midnight under PostgreSQL's tz data, while backend3 computes midnights with chrono-tz's. Should ADR 0010's tz-data procedure cover both sides, with a test that they agree?": "Amend ADR 0010: a parity test and a two-sided procedure". Its consequence: "posts-schema adds a test that compares PostgreSQL's and chrono-tz's Budapest midnights over the supported range, and the tz-data procedure names both sides."

The slice plan moved the test from `posts-schema` into this ADR's PR, so the amending ADR lands with it. The test evaluates the check's expression on its own, because no table carries the check yet.

Writing the test left three points that D96's answer does not reach: the days after the end of chrono-tz's table (item 3), whether a production PostgreSQL move waits for compose.yaml, which section 3 read into the answer, and how backend3 moves the stored values of a day whose midnight moves. The third decision register asked about each (D122 to D124), and the maintainer answered all three on 2026-11-01 (research: DECISIONS R25), each with the recommended option. Each item gives the register's question, the answer, and the consequence the register gave for that option (research: third decision register D122 to D124). The consequences name this ADR's text before the answers; the sections below carry the edits they describe.

- **D122, the days after 2099.** The question: "chrono-tz 0.10.4 stays on winter time after its Budapest table ends (2099-10-25). PostgreSQL 18.6 with tz data 2026c keeps changing to summer time. Once posts-schema adds the midnight check, the database refuses a post dated, for example, 2100-07-01. Should backend3 refuse days after 2099 itself, and if so, where?": "Refuse them on the field, after CHRONO_TZ_LAST_CHANGE_YEAR". Its consequence: "A new `BudapestTimeError` variant refuses every calendar day after 31 December of `CHRONO_TZ_LAST_CHANGE_YEAR`, winter days included. The rule is then one year boundary, not the 210 or 217 summer days of each year. The check goes beside `date_to_midnight` in `src/domain/budapest.rs`. Two places call it: `CalendarDate::to_midnight`, which every admin write of a day uses, and the importers' conversion of legacy days. `date_to_midnight` itself does not change, so the public month and grid bounds still convert every year up to 9999 (public-api.md 7.7: 9999 gives 200). Point 6 then applies. The first slice that writes a calendar day (posts-properties) maps the variant to a field error, as it maps NoMidnight, and the importer stops and reports the row. The bound moves with the constant, and the existing unit test keeps the constant in step with chrono-tz's table. The wire forms keep 0001 to 9999, and event wall times are not affected. ADR 0041's compared range then covers every day backend3 can store, which settles its narrowing. The CalendarDate round-trip property test draws days up to 9999, so it accepts the new error after 2099."
- **D123, the production step.** The question: "ADR 0041 §3 reads the consequence of D96's answer, 'the tz-data procedure names both sides', as an ordering rule: an Image Updater PR that moves production's PostgreSQL to an image whose tz data differs from compose.yaml's merges only after a backend3 PR has moved compose.yaml to that tag and its Test job has passed. Its consequence: "§3 drops 'so it waits on the maintainer's confirmation', its Follow-up bullet and the ADR index row's 'a reading that awaits the maintainer's confirmation' go, and ADR 0041 quotes D123. AGENTS.md and CLAUDE.md already state the step without that mark, so no other text or code changes. Before each PostgreSQL Image Updater PR, you read one file from the new image. When its tz data differs, the merge waits for one backend3 PR that moves compose.yaml, and its Test job. When the parity test fails, the merge waits until chrono-tz follows, or you decide. Production then runs only tz data that has passed a Test job, unless you decide otherwise or the node pulls a rebuilt image under the same tag (ADR 0041, Negative)."
- **D124, moving the stored values of a moved day.** The question: "New tz data can move the Budapest midnight of days that already have stored values. ## Decision

### 1. What this ADR amends

| Amended text | Change | Section |
|---|---|---|
| ADR 0010, Consequences, the first "Negative" item, from "A tz-data bump PR states the new tz data version." to its end | Replaced by the two-sided procedure of section 3. Its events step keeps ADR 0010's wording, and the item's first sentences, on why event times depend on the rules, stand. | 3 |
| ADR 0010, "What must be true in code and tests" | Gains the parity test, the snapshot of backend3's midnights and the two checks on chrono-tz's data of section 2, and the tests of the stored-day bound. | 2 |
| ADR 0010 point 2, the days that the conversion module refuses | Gains every day after 31 December of `budapest::CHRONO_TZ_LAST_CHANGE_YEAR`, refused when a day is stored (D122). Point 6's answer, a validation error on the field in the admin and a reported row in the importer, applies to it. | 2 |

Everything else in ADR 0010 holds as written: the check of point 2, the compiled-in tz database of point 5 and the conversion rules of point 6 included. SQL still never turns a day or a wall time into an instant. ADR 0018 §1.3, which states the same check, does not change.

### 2. The parity test and backend3's pinned midnights

- **What it asserts.** For every day of the compared range, the Budapest midnights that backend3 finds through `src/domain/budapest.rs` are the midnights that PostgreSQL finds with the check's expression, `::time = time '00:00'`, together with the day that `::date` derives: none, one or two instants, the same on both sides. A failure lists the first 20 days that differ with both sides' instants, counts all of them, and names both tz data versions. `tests/tz_parity/mod.rs`, `postgresql_and_backend3_agree_on_every_budapest_midnight`.
- **The compared range.** From 0001-01-01, the first day that the wire forms carry (`date_text::FIRST_YEAR`; [public-api.md](../public-api.md) DEC-13), to the end of the last year whose Budapest clock changes chrono-tz lists, `budapest::CHRONO_TZ_LAST_CHANGE_YEAR` (2099-12-31 with chrono-tz 0.10.4).
- **Every day that backend3 stores.** The wire forms take the years 1 to 9999 (`date_text::LAST_YEAR`, DEC-13), so read literally, the consequence of D96's option, "over the supported range", would compare every day to 9999-12-31, and that comparison fails today (Context, item 3, and Alternatives). backend3 stores no calendar day after the compared range (next item), so the range covers every day that a calendar-day column can hold, the values that the check and `::date` see. This settles the narrowing (D122).
- **The days after the range are not stored.** The days from 2100 on differ today (Context, item 3) and are not compared: the test would fail on facts that only a chrono-tz with a longer table changes. `budapest::date_to_stored_midnight`, beside `date_to_midnight`, refuses every day after 31 December of `CHRONO_TZ_LAST_CHANGE_YEAR` with `BudapestTimeError::AfterTzTable`, winter days included, although the two sides agree on them: the rule is one year boundary, not the 210 or 217 summer days of each year. Every conversion of a day that is to be stored goes through it: `CalendarDate::to_midnight`, which every admin write of a day uses, and the importers' conversion of legacy days. ADR 0010 point 6 applies: the admin answers the error with a validation error on the field, as it answers `NoMidnight`, and the importer stops and reports the row. `date_to_midnight` itself does not change, so bounds that are compared but never stored, such as the public month and grid bounds, still convert every year up to 9999 ([public-api.md](../public-api.md) 7.7 and 7.10). The wire forms keep the years 1 to 9999, and event wall times are not affected. The bound moves with the constant ("The checks on chrono-tz's data", below).
- **How both sides find a day's midnights.** Every offset that Budapest has used lies between `+01:00` and `+02:00` (local mean time, until 1890, was `+01:16:20`), so a midnight lies between two hours and one hour before 00:00 UTC of the day. Each side reads its offset three hours before and one hour after 00:00 UTC; each offset `o` gives the candidate `00:00 UTC - o`, which is a midnight when its Budapest wall time is 00:00:00 on that day. That finds every midnight unless the offset changes twice within those four hours, which the tz data never does for Budapest: its changes lie months apart (at least 119 days in chrono-tz 0.10.4's table). On backend3's side the test also checks, for every day, that the first midnight found is the one `date_to_midnight` writes and that a day with none is a day it refuses. backend3's midnights go to PostgreSQL as runs of consecutive days with the same midnights (about 300), one query compares every day and returns only the days that differ, and the whole test takes a few seconds.
- **backend3's midnights, pinned.** The parity test compares the two sides only with each other, so a change that moves a midnight on both sides at once would pass it: one PR that moves chrono-tz and compose.yaml's image together, or a chrono-tz release that catches up with tz data that PostgreSQL already has. `backend3_keeps_the_recorded_budapest_midnight_of_every_day` therefore pins backend3's runs over the compared range in the committed snapshot `tests/tz_parity/snapshots/budapest_midnights.snap`: one line per run, its days and the UTC offset of each midnight (287 runs with chrono-tz 0.10.4). Any chrono-tz change that moves a midnight fails it, whatever PostgreSQL does, and its diff shows each changed run with the old and the new offsets. The parity test then carries the snapshot over to PostgreSQL. CI sets `INSTA_UPDATE=no`, so a mismatch only fails there; a PR accepts a new snapshot only together with the steps of section 3 for the days it moves.
- **ADR 0010 point 2's statement.** The same test also pins the eleven days with no midnight or two (1916-10-01, 1945-11-01, 1954-05-23, 1980-04-06, 1980-09-28, 1981-03-29, 1981-09-27, 1982-03-28, 1982-09-26, 1983-03-27 and 1983-09-25) with their midnights, so every other day of the range, every day from 1984 on included, has exactly one. This list stands on its own, so that a snapshot accepted in a hurry cannot lose or add such a day. The parity test carries it over to PostgreSQL.
- **The checks on chrono-tz's data.** The unit test `the_zone_and_the_recorded_tz_data` fails until `TZ_DATA_VERSION` records chrono-tz's tz data version, as before. The new `chrono_tz_lists_clock_changes_until_the_recorded_year` fails until `CHRONO_TZ_LAST_CHANGE_YEAR` is the last year with summer time in chrono-tz's table, so moving the constant also moves the end of the compared range and the last day that backend3 stores. `a_stored_day_ends_with_the_last_year_of_chrono_tzs_table` pins the last day stored, the first day refused and a winter day after it; a property test checks that `date_to_stored_midnight` gives `date_to_midnight`'s result up to the bound and refuses every later day, and the `CalendarDate` round trip accepts the refusal only after the bound.
- **The comparison itself.** `the_comparison_reports_each_day_that_differs` shows that the comparison fails where the two sides differ, that it counts every differing day when there are more than it lists, and that PostgreSQL's tz data version can be read for the failure message. `postgresql_finds_no_midnight_and_two_midnights_as_backend3_does` pins a day with none, a day with two and a day of local mean time.
- **The role it needs.** The version is read with `pg_read_file` from the image's `/usr/share/zoneinfo/tzdata.zi`, which needs a superuser or a member of `pg_read_server_files`. compose.yaml's `loco` is the image's bootstrap superuser, so CI and the local compose database qualify; a database whose test role is neither fails the version check of `the_comparison_reports_each_day_that_differs`, and the parity test's failure message shows the version as unknown.
- **Where it runs.** In the Test job's two nextest runs, under both process `TZ` values (ADR 0010), against compose.yaml's PostgreSQL, and locally with the rest of the suite. It adds no job and no step (ADR 0022 §3, [ADR 0029](0029-no-filters-or-job-conditions-on-required-ci-jobs.md)).
- **What it does not compare.** Wall times at other instants: an event's start and end convert only in backend3 (point 5), and the events step of section 3 covers a change of their rules.

### 3. The tz-data procedure, both sides

The two sides change on separate schedules, so a change to either one is a change to the pair. The tests of section 2 are the gate.

**backend3's side: a PR that moves chrono-tz**

1. records the new tz data version in `budapest::TZ_DATA_VERSION` and in the chrono-tz comment of `Cargo.toml`, and the end of chrono-tz's Budapest table in `budapest::CHRONO_TZ_LAST_CHANGE_YEAR` if it moved; the two unit tests of section 2 fail until it does;
2. passes the snapshot test of section 2; if the snapshot changes, the PR commits the reviewed new snapshot and follows the steps below for the stored days whose midnight moved;
3. passes the parity test against compose.yaml's PostgreSQL;
4. states both sides' tz data versions in its body;
5. events: before it merges, the operator runs a read-only task `events_tz_report` on staging, against the newest copy of the production data, under the old and the new build. The task prints the Europe/Budapest wall times of future events. The operator diffs the two outputs and re-enters any event that moved. Only the count of changed events goes into the PR, because production data never goes into a PR (ADR 0003). Until `events-import` adds the task, no event is stored and this step has nothing to compare.

**PostgreSQL's side**

1. **compose.yaml.** A backend3 PR that moves compose.yaml's PostgreSQL image (its tag and digest) passes the parity test and states the image's tz data version: the first line of `/usr/share/zoneinfo/tzdata.zi` in the image, which the test's failure message also shows.
2. **Production.** Before the operator merges an Image Updater PR in website_k8s that moves production's PostgreSQL to a new tag, they read the tz data version of that image in the same way. If it differs from that of compose.yaml's image, compose.yaml first moves to the same tag, with its digest, in a backend3 PR, and the website_k8s PR merges after that PR's Test job has passed. The minor of compose.yaml may still lag production's when the tz data is the same. This ordering is how this ADR reads D96's "the tz-data procedure names both sides", and it ties website_k8s merges to a backend3 PR; the maintainer confirmed it as written (D123).

**When the parity test fails**, the change that brought new tz data to one side does not merge: the backend3 PR stays open, or the website_k8s PR waits. The listed days show where the sides disagree. The other side then follows to tz data that agrees, through a chrono-tz release or a PostgreSQL image that carries it. When both sides need the new data, one backend3 PR moves chrono-tz and compose.yaml together, so that the test compares the new pair, and production's PostgreSQL moves in the release that deploys that backend3 build. If that cannot happen in time, for example for a PostgreSQL security release, the maintainer decides.

**When new tz data moves the midnight of a stored day**, for a change of Hungary's rules in future years or a correction of past ones, a stored value on that day stops being a Budapest midnight once a side carries the new data: backend3 reads it as no day, PostgreSQL refuses its next update (a check runs only on writes), and an index on `(date AT TIME ZONE 'Europe/Budapest')::date` still holds the day that the old data gave. The tests of section 2 name those days, with the old and the new midnights, whichever side moves first: a chrono-tz change fails the snapshot test, whose diff shows each changed run, also when compose.yaml's image moves in the same PR; a PostgreSQL image fails the parity test, which lists each day with both sides' instants, as long as chrono-tz still has the old data. The change that brings the new data to both sides then also, in the same release:

1. counts the stored calendar-day values on those days on staging, with the newest copy of the production data, and puts only the count into the PR, as for events. A value is on such a day when it is that day's old midnight, as the listing gives it;
2. moves each such value to the new midnight of that day. The new instant comes from `budapest::date_to_stored_midnight` in backend3's code, the conversion of every day that is to be stored (section 2), never from SQL, because SQL never turns a day into an instant (section 1, ADR 0010 point 5). D124's consequence, written before D122's answer, names `date_to_midnight(day)`; a stored day lies within the bound of section 2, so both give the same instant. The day is the one whose old midnight the value is, as the listing gives it, not the day that `AT TIME ZONE` derives, which under the new data can already be the day before. backend3 runs this move as a one-off Loco task under the task lock ([ADR 0016](0016-no-redis-in-memory-cache-postgres-queue-cronjob-tasks.md) §4, recipe 6 of the project skill), run by the maintainer (D124). The change that first needs it adds the task: a constant in the task lists the moved days and their old midnights from the snapshot diff, reviewed in the PR, and in one transaction the task moves each value found at an old midnight to `date_to_stored_midnight(day)`, so a second run changes nothing; while PostgreSQL still has the old data, the check refuses the first new instant and nothing changes. The maintainer runs it with `backend3-cli task <name>` through `oc exec`, as [cutover.md](../cutover.md) §6 phase 4 runs the import: first on staging, where the number it moves is step 1's count, then in production once both the deploy and PostgreSQL's move are done. Boot does not change. No task is written now, because no calendar day is stored yet;
3. runs `REINDEX` on every index whose expression uses `AT TIME ZONE`.

## Consequences

**Positive**

- A divergence between the two tz databases shows as a failing test with its days listed, before an editor meets a refused write or a stored day that does not read back.
- A chrono-tz change that moves any day's midnight fails with the changed runs listed, also when PostgreSQL's side moves in the same PR, so the stored values on those days can be counted and moved.
- Every PR that moves either side's tz data states both versions, so the pair is on record.
- ADR 0010 point 2's statement about the days with no midnight or two is checked over the range, on both sides, with the eleven days named.
- A calendar day after 2099, almost certainly a typing mistake, is refused on its field in the admin and as a reported row in the importer, in winter as in summer, instead of reaching the check as a server error on summer days only. The compared range covers every day that backend3 stores.
- The tests need no new job, container or tool: they run on compose.yaml's PostgreSQL in the existing Test job.

**Negative**

- The test sees compose.yaml's PostgreSQL, not production's: production is covered only through the operator step of section 3. Production names its image by tag only, so if the node pulls the same tag again after the image was rebuilt, it may run other tz data that no backend3 run has compared until the next compose.yaml move.
- A PostgreSQL bump in production waits for a backend3 PR when the new image's tz data differs from compose.yaml's.
- No calendar day after 31 December of `CHRONO_TZ_LAST_CHANGE_YEAR` (2099 with chrono-tz 0.10.4) can be stored, winter days included, although the wire forms read it. The bound moves only with a chrono-tz whose table reaches further.
- When new tz data moves the midnight of a stored day, the values on that day read as server errors between the deploy and the maintainer's run of the task of section 3, step 2.
- A chrono-tz release that changes the snapshot needs a reviewed snapshot update, even when no stored day lies on a changed day.
- The version check needs a test role that may read the image's tz data file (section 2, "The role it needs"), which the suite did not need before.
- The tests add a few seconds to each of the Test job's two runs.

- `posts-properties`, the first admin write of a calendar day, maps `BudapestTimeError::AfterTzTable` from `CalendarDate::to_midnight` to a validation error on the field, as it maps `NoMidnight` (ADR 0010 point 6), and the later calendar-day writes (`canteen-day-form`, `diaktoll-admin`) do the same (D122).
- The importers' conversion of legacy days (`posts-import-rows`, `posts-import-dates` and `canteen-import-days`) goes through `budapest::date_to_stored_midnight` and turns `AfterTzTable`, as `NoMidnight`, into a refusal that stops the import and reports the row ([data-migration.md](../data-migration.md) §4.2; ADR 0010 point 6; D122).
- The change that first brings tz data that moves the midnight of a stored day adds the one-off task of section 3, step 2, and the maintainer runs it (D124).

**What must be true in code and tests**

- `tests/tz_parity/mod.rs`: the parity test over the compared range; the snapshot test of backend3's midnights over the same range, with the eleven days of ADR 0010 point 2 pinned in the test itself; the test that the comparison reports each differing day and counts beyond the ones it lists; and the test of the days with none, two and local-mean-time midnights.
- `src/domain/budapest.rs`: the unit tests of `TZ_DATA_VERSION` and `CHRONO_TZ_LAST_CHANGE_YEAR`; the unit test of the stored-day bound (the last day stored, the first day refused and a winter day after it) and the property that `date_to_stored_midnight` agrees with `date_to_midnight` up to the bound and refuses every later day.
- `src/dtos/shared.rs`: `CalendarDate::to_midnight` converts through `date_to_stored_midnight`, and its round-trip property accepts `AfterTzTable` only after the bound.
- The tests run in both process-`TZ` runs of the Test job, against compose.yaml's PostgreSQL.

## Alternatives considered

| Option | Source | Why not |
|---|---|---|
| Amend ADR 0010: a parity test and a two-sided procedure | second decision register D96 | Chosen (research: DECISIONS R15 (D96)). |
| Keep the procedure as it is | second decision register D96 | Not chosen: after a tz change, a divergence would show up as refused writes of dates on the affected days. |
| Compare only which days have no midnight or two, as the reviewer did | this ADR | Misses a midnight that moves: from 2100 on the lists match while every summer day differs. |
| Compare the years 1890 to 2200 | this ADR | Fails today on the summer days from 2100 on, and leaves out the years before 1890 that the wire forms carry, which cost little to compare. |
| Compare every day from 0001-01-01 to 9999-12-31, the years of the wire forms (DEC-13) | the consequence of D96's option, "over the supported range", read literally | Not chosen: it fails today on every summer day from 2100 on (217 in 2100 alone, Context item 3), facts that no backend3 PR can change until chrono-tz's table reaches further. backend3 stores no day after `CHRONO_TZ_LAST_CHANGE_YEAR` (D122), so the compared range already covers every stored day. |
| Refuse the calendar days after `CHRONO_TZ_LAST_CHANGE_YEAR` on the field | third decision register D122 | Chosen (research: DECISIONS R25 (D122)). |
| Accept the database refusal of the days after 2099 | third decision register D122 | Not chosen: the editor would get a server error with no field message on a summer day, while a winter day of the same year saves, and the importer would get the database error instead of point 6's row refusal. |
| Cap every date field at 2099-12-31 (`date_text::LAST_YEAR`) | third decision register D122 | Not chosen: it caps event wall times too, which have no midnight check, and a later date refuses the whole body (`422 invalid_body`, D74) instead of the field; the cap would not move with a chrono-tz whose table reaches further. |
| Confirm the production step of section 3 as written | third decision register D123 | Chosen (research: DECISIONS R25 (D123)). |
| Exempt PostgreSQL security releases: website_k8s first, the compose.yaml PR after | third decision register D123 | Not chosen: four of the five released 18.x minors fixed CVEs, so most moves would skip the hold, and until the follow-up's Test job runs production would carry tz data that nothing has compared, while section 3 already leaves an urgent case to the maintainer. |
| Let production's PostgreSQL move freely, with compose.yaml following | third decision register D123 | Not chosen: every move could leave production on tz data that nothing has compared, and nothing would remind anyone to move compose.yaml. |
| Move the stored values of a moved day with a one-off Loco task under the task lock, run by the maintainer | third decision register D124 | Chosen (research: DECISIONS R25 (D124)). |
| A migration-like step in backend3's code, run at boot | third decision register D124 | Not chosen: the step would have to find the moment when both sides have the new data, add a write to a boot that must start on a read-only database (ADR 0003), and stay in every start until a PR removes it. |
| Decide the mechanism when a stored day's midnight first moves | third decision register D124 | Not chosen: nothing in the answer depends on which tz change comes, and a later answer would be needed while that change is held. |
| Compare the two sides only, with no snapshot of backend3's midnights | this ADR | Passes when one PR moves both sides to tz data that moves a midnight, so the stored values on those days would go unnamed and the steps of section 3 would have no input. |
| Move the stored values of a moved day with a forward migration in SQL | this ADR | SQL would turn a day into an instant, which section 1 and ADR 0010 point 5 rule out, and the migration crate cannot use `src/domain/budapest.rs`: backend3 depends on `migration`, not the other way round. |
| A boot check of backend3's midnights against the running database | this ADR | Would see production's image as it runs, but costs seconds of database time at every start on the edge node and turns a tz-data difference into a failed start; the answer chose a test and a procedure. |
