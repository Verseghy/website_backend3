# 0036. Guardrails for Redis clients in new pods, argocd app patch and inline manifests

- Status: Accepted (2026-10-26)
- Decision questions: none: amends [ADR 0035](0035-guardrails-for-in-cluster-redis-argo-cd-patches-and-deletion.md) §2 to §5, its "Negative and risks" and its "Follow-up work", which amend ADR 0028 and, through it, ADR 0024 §4. It records the maintainer's answer of 2026-10-26 to D110 of the third decision register (research: DECISIONS R18).

## Context

[ADR 0035](0035-guardrails-for-in-cluster-redis-argo-cd-patches-and-deletion.md) closed the three paths that [ADR 0028](0028-guardrails-as-built-wider-checks-and-a-fail-closed-hook.md) had left open. Its "Negative and risks" recorded five more paths of the same data-loss class, which no answer covered, so the hook let them run: a `redis-cli` in a pod that the agent starts; Redis programs other than `redis-cli`; `argocd app patch` of an Application's own finalizers; the deletion-approved annotation in a manifest that `oc apply`, `oc create` or `oc replace` reads; and text that only the shell computes. Blocking any of them needed another answer or an amending ADR first ([ADR 0001](0001-record-architecture-decisions.md) §6). Its Context said that this ADR would record the answer to D110, which asked about them, and its "Follow-up work" left two spellings of its own rules to the same PR: a heredoc that `xargs` or `parallel` read, and a here-string that `cat` passes on.

### 2. The new checks

Check 1 also blocks, in every spelling and wrapper the hook already handles:

1. **An `argocd app patch` that changes an Application's finalizers**: the finalizer match of the patch rule of ADR 0028 §5 item 3, as ADR 0035 §2 reads it. Its words name `finalizers`, compared in lower case and decoded as the patch decoders read them, additions included, or it replaces or removes the whole object or its whole metadata, which ADR 0035 §2 counts as a finalizer change (a JSON patch on `""` or `/metadata`, `$patch: replace|delete`, `$retainKeys`). Every word after `argocd` is read, so the patch counts wherever `--patch` stands, for both `--type` values. The subcommand is found as ADR 0035 §2 item 1 finds `confirm-deletion`, and `--type`, a string in every argocd subcommand that has it, joins the value options the hook skips. The reclaim-policy match is not applied: the answer names the finalizer match, and an Application has no reclaim policy. A patch of anything else (`--patch '{"spec":{"syncPolicy":...}}'`) stays allowed.
2. **An inline manifest that names `deletion-approved`**: a manifest that `oc apply`, `oc create` or `oc replace` reads from the command text. The hook takes as one every text that such an oc gets on stdin, whatever its `-f` says, as ADR 0028 §4 takes every text that `oc exec` gets: a heredoc (quoted, unquoted or `<<-`), also through `cat` (`cat <<'EOF' | oc apply -f -`, also when the pipeline goes on after the body), a here-string, piped `echo` or `printf` text, also through further stages and from a subshell or brace group (`{ echo '...'; } | oc apply -f -`), and `< <(echo '...')`; and the `echo` or `printf` output, or the heredoc, of a process substitution that it reads as its file (`oc apply -f <(echo '...')`, `oc apply -f <(cat <<'EOF' ...)`), in every place of section 3, inside a `sh -c`, `bash -c`, `eval` or `ssh` script included. Under `xargs` or `parallel` that text is the oc's arguments instead, as ADR 0035 §2 reads it. The manifest is matched as ADR 0035 §2 item 3 matches a word: `deletion-approved` in lower case, with YAML and JSON escapes decoded and blanks dropped. So a manifest that only mentions the key, a `--dry-run=server` one included, is blocked too, as the answer's false positives say.

Check 2 also blocks:

3. **The other Redis clients**: `redis-benchmark`, `valkey-cli` and `keydb-cli` join `redis-cli` wherever ADR 0035 §2 item 4 blocks it, and in the new places of item 4 below: in the command part of `oc exec`, `oc rsh` and `oc debug`, by any path, in quotes, after `env` or `timeout`, in a `sh -c` script, and in the text those read on stdin. Each one is a trigger word of the hook's fast path, as `redis-cli` is, so the chunk of a long pipeline that holds only the `echo` is still read. None of them is checked on the agent's own host, a pod, container or file named like one is not the command part, and they do not join the listed commands of check 2, for ADR 0035 §2 item 4's reasons.
4. **A Redis client as the command of a pod that the agent starts**:
   - in the command part of `oc run`: every positional word after the pod's NAME, before `--` and after it, as kubectl hands them to the container (Context), so `oc run tmp --image=redis --command redis-cli -- -h <service> FLUSHALL` and `oc run tmp --image=redis:6.2-alpine redis-cli -- ...` count. An image named like a client (`--image redis-cli`) and the pod's own NAME (`oc run redis-cli --image=redis -- redis-server`) are not the command part;
   - in its `--overrides` JSON, where the client is found by its name, since the JSON can set the container's command or arguments in fields the hook does not parse;
   - in the text that `oc run` passes to the pod on stdin (a heredoc, also through `cat`, a here-string, piped `echo` or `printf` text, what a subshell or brace group pipes on, `< <(echo ...)`, and a heredoc whose `cat` output fills in its `--overrides`), read for a Redis client whatever the pod's program, by its name as in a manifest (`subprocess.run(["redis-cli", "FLUSHALL"])` counts) and by the shell words that ADR 0035 §2 item 4 reads, as ADR 0028 §4 reads the stdin of `oc exec`, which errs towards blocking. It is not read as commands there: the pod's program need not be a shell, and a shell word in the command still makes the hook read the text as a script, as before;
   - in the command part of `oc create job`, `cronjob`, `deployment` and `deploymentconfig`, and their aliases `cj`, `deploy` and `dc`: every positional word after the NAME, before `--` and after it, as for `oc run`; oc refuses a second word before `--` ("exactly one NAME is required"), so there the words before it only err towards blocking. The subcommand is found as oc's verb is, in both readings of ADR 0035 §2 (`oc create --schedule '*/5 * * * *' cronjob ...`, `oc create --save-config job ...`), and the pod-start verbs are also read on the words as the lexer gives them, so that an option value with blanks (`--schedule '*/5 * * * *'`, `--env 'A=b c'`), which the hook's other readings cut into words, cannot hide the subcommand or the command part. Any other subcommand (`oc create configmap ...`) runs no command;
   - in an inline manifest, in every form of item 2, where the client is found by its name, so a Pod, Job, CronJob or Deployment that runs one is blocked, and so is a manifest that only mentions one, a `--dry-run=server` one included.

   A client counts in the command part as ADR 0035 §2 item 4 counts one, by the program name of a word. In `--overrides` JSON, in a manifest and in the text that `oc run` passes on stdin, the text is read three ways, and each counts: decoded as a patch is; the same with its blanks removed, because a YAML escaped line break in a double-quoted scalar folds a name across lines (`"redis-\`, then `cli"`); and with its quotes and backslashes removed, as the pod's shell removes them from a script string (`"redis-c'l'i FLUSHALL"`). In each reading a name counts where it stands as a word: not after a letter, digit, `_`, `.` or `-`, and not before a letter, digit, `_` or `-`. So `"/usr/local/bin/redis-cli"` and `[redis-cli, FLUSHALL]` count, and a Service `redis-cli-0` or a ConfigMap `my-redis-cli` does not. Only the Redis clients count in a pod the agent starts: the answer names them, and a database command there keeps the target check that check 2 gives every command word (ADR 0035 §2 item 4: `oc run ... -- psql -h postgres` is blocked, `-h localhost` is not). An `oc exec` inside such a pod's command still counts whole (`oc run x --image=y -- oc exec pg-0 -- psql` is blocked).

Each block reason names ADR 0024 §4, ADR 0028, ADR 0035 and this ADR, and says what was refused and what to do instead. The reasons for the inline manifests and the text `oc run` passes on stdin say that the hook does not tell a text that sets the key or runs the client from one that only mentions it. They do not suggest passing the manifest as a file, since a manifest file is a recorded gap; they say how to pass a commit message, PR or issue body from a file, for the false positive that "Negative and risks" records.

### 3. Readings fixed in the accepted rules

These are spellings of the rules that ADR 0028 and ADR 0035 accepted, not new paths, so reading them is a fix of those rules (ADR 0001 §5). ADR 0035's "Follow-up work" left two of them to this ADR, the heredoc that `xargs` or `parallel` read and the here-string that `cat` passes on:

- **A heredoc on any line, after a `<` and beside others.** The hook reads the command line by line and takes every heredoc operator on a line, in order, each with the lines up to its delimiter; an operator whose delimiter never comes is none (`$((1<<2))`). Before, it found only the first one, only on the first line and only before any `<` there (Context), so a heredoc that a shell, `oc exec`, `oc rsh` or `oc debug` read on a later line, inside `<(cat <<'EOF' ...)` or as the second of its line was lexed as command text, and a commit message there was read as commands. Every receiver on a line reads every body on it, which errs towards blocking where bash gives a command only its last heredoc or each command its own. The website_k8s guardrails branch's hook has the same pattern, so its port takes this fix too (section 6).
- **A `<<` inside quotes.** A `<<` inside quotes is no operator, so the lines after it are commands (Context): `echo '<<X'`, a line `<<EOF2"` that ends a multi-line string, or a commit message that mentions `<<EOF2`, followed by `oc delete ns web` and a line `EOF2`, must not hide the `oc delete`. The hook reads the command twice where that matters: once with every operator taken as a heredoc, as above, and once with only the operators that a small model of bash's quoting finds surely outside quotes, and each reading's segments are checked. The model reads single and double quotes, a `$(...)` with plain content and simple strings (also within double quotes, where quoting starts afresh, so `git commit -m "$(cat <<'EOF'` stays a heredoc), an arithmetic `$((...))`, `$` before anything else and a comment that starts a word; anything else on a line (a backslash, a backtick, `$'...'`, a nested `$(...)`) makes it unsure from there on, so the second reading takes no more operators. The first reading still reads a real heredoc after quoting the model does not know (`echo don\'t`, then `oc exec -i redis-0 -- sh <<'EOF'`), and the second the commands after a quoted `<<`. A text without `<<`, or one where both readings agree, is read once.
- **A heredoc inside a script that a shell runs.** The text of a `sh -c` or `bash -c` string, the arguments of `eval`, `ssh` and `watch`, a here-string or piped text that a shell reads, what `oc exec`, `oc rsh` or `oc debug` read on stdin, the output of a substitution that the shell runs and a `$(...)` within double quotes have their heredocs read the same way before they are split as commands. So `sh -c 'oc apply -f - <<EOF ... EOF'` reads the manifest, `eval 'oc exec -i pg-0 -- sh <<EOF ... EOF'` the script in the cluster, and `sh -c 'cat > notes.txt <<EOF ... EOF'` the data as data.
- **A pipeline that goes on after the bodies.** When a heredoc's receiving line ends in `|` or `|&`, bash goes on with the pipeline on the line after the bodies (Context), and when that line closes a group (`( cat <<'EOF'`, the body, `EOF`, then `) | oc apply -f -`) the group's output goes on too. The hook reads that next line as part of the receiving line, so its `oc apply`, `oc run`, `oc exec`, `xargs` or shell reads the body.
- **What a subshell or brace group pipes on, and `< <(...)`.** The `echo` or `printf` text inside `( ... )` or `{ ...; }` reaches a `|` right after the group as piped text does, also after a redirection (`( echo '...' ) 2>/dev/null | sh`), and a process substitution that a bare `<` redirects to stdin (`oc exec -i pod -- sh < <(echo '...')`) gives its `echo` or `printf` text to the command as a here-string does, for `oc exec`, `oc rsh`, `oc debug`, `oc run`, `oc apply`, `oc create`, `oc replace` and `xargs` (a shell already read it as a script, ADR 0035 §2). Its `/dev/fd/63` is then not an argument: `xargs oc < <(echo delete ns web)` runs `oc delete ns web`.
- **A quoted option value with a separator.** The receiver of a heredoc is also found with the `;`, `&`, `|`, `(` and `)` inside quoted strings blanked, so `oc --selector='a|b' apply -f - <<'EOF'` reads the manifest, and `oc --selector='a|b' exec -i pod -- sh <<'EOF'` the script in the cluster.
- **A heredoc that `xargs` or GNU `parallel` read**, directly or through `cat` (`xargs oc <<'EOF'`, `parallel oc delete <<'EOF'`, `cat <<'EOF' | xargs oc`): its body is also put on the receiving line as a here-string, which the hook then passes to the command they run as its arguments, as ADR 0035 §2 reads `xargs oc <<< '...'`. A body that a shell on the line reads is still a script.
- **A here-string that `cat` passes on through a pipe** (`cat <<< 'delete ns web' | xargs oc`, `cat <<< 'redis-cli flushall' | oc exec -i redis-0 -- sh`, `cat <<< '...' | sh`): it reaches the next stage as piped `echo` text does. A `cat` that also names files counts too, which errs towards blocking.
- **The value options of `oc run` and `oc create`.** The hook skips the value of each option it knows to take one (ADR 0035 §2). Since it now reads the positional words of `oc run`, `oc create` and the four create subcommands, their value options join the list from the oc 4.22 client: `--annotations`, `--env`, `--field-manager`, `--from`, `--image-pull-policy`, `--labels`, `--override-type`, `--overrides`, `--port`, `-r`, `--replicas`, `--restart` and `--schedule`. `--validate`, like `--dry-run` and `--cascade`, has a value of its own when it stands alone and is not listed. When the oc 4.22 client is on the PATH, a test compares the list with the help of these verbs too.
- **The program through a process substitution.** The hook gave jq its commented program as one command-line argument, and this ADR's readings make the program longer than one argument may be (Context), which would block every command. jq now reads it from a process substitution (`jq -r -f <(printf '%s' "$GUARD_JQ")`): `printf` is a bash builtin, so no argument limit applies, and the substitution is a pipe, so it needs no temporary file, as a here-string of that size would. A `/dev/fd` path that cannot be opened makes jq fail, which blocks, so the hook still fails closed.

The text that the hook gives these new readings, an inline manifest and what `oc run` passes to its pod, is data, not commands. The hook keeps each one as a synthetic segment whose text is base64-encoded, so that no other check reads it as words: a ConfigMap that quotes `oc exec pod -- psql` does not count as that command, and only the rules of section 2 decode the text.

```json
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/guard-bash.sh",
            "args": [],
            "onFailure": "block"
          }
        ]
      }
    ]
  }
}
```

- **The new deny rule** is the form of section 2 item 1 that a rule on the command text can match, as ADR 0035 §3 has for `argocd app patch-resource`: `Bash(argocd app patch *finalizers*)`. The space after `patch` keeps it from matching `patch-resource`, which has rules of its own. The hook covers every other spelling, and the whole-object and whole-metadata patches, which no text rule can match, as for `oc patch`.
- **No deny rule for the Redis clients in a pod the agent starts.** They belong to check 2, which has no deny rules (ADR 0028 §3, ADR 0035 §3), and a text rule such as `Bash(oc run *redis-cli*)` would also refuse a pod or image named like the client, which the hook allows on purpose.
- **No deny rule for inline manifests.** A rule such as `Bash(oc apply *deletion-approved*)` would refuse `oc apply -f deletion-approved.yaml`, a file the hook does not read, and would miss `cat <<'EOF' | oc apply -f -`, where the key is not after `oc apply`. Every deny rule must have a hook check behind it (ADR 0035 §4), and the hook reads only the text on stdin.
- The hook entry is unchanged: exec form with `"args": []` and `"onFailure": "block"` (ADR 0028 §3).

## Consequences

**Positive**

- Every path of D110's answer that the command text shows is closed: a Redis client in a pod that `oc run` or `oc create job|cronjob|deployment|deploymentconfig` starts, in its `--overrides` and its stdin, or that an inline manifest describes; `redis-benchmark`, which ships in the clusters' Redis image and can send FLUSHALL through the same `oc exec` that refuses `redis-cli`, and the clients of Redis's forks; a finalizer change of an Application through `argocd app patch`; and the deletion-approved annotation in an inline manifest.
- Each new check extends a rule the hook already has: the in-cluster rule's command part and its client list, the patch rule's finalizer match, the argocd subcommand finder, the annotation match and the reading of a heredoc, a here-string and piped text.
- A heredoc on a later line, after a `<`, beside another or inside a script that a shell runs, a heredoc that `xargs` reads, a here-string that `cat` passes on, a pipeline that goes on after a body, what a group pipes on and `< <(...)` are read as their accepted rules ask, for every check, ADR 0028's included, and a `<<` inside quotes no longer hides the commands after it.

**Negative and risks**

These replace ADR 0035's bullets on other Redis programs, on a `redis-cli` in a pod that the agent starts, on `argocd app patch` of an Application's own finalizers and on the heredoc that `xargs` reads and the here-string that `cat` passes on. Its bullet on the annotation in a manifest holds for the manifests that the command text does not show. Its other bullets hold.

- Running a Redis client in a pod that the agent starts, `redis-cli ping` and a benchmark included, changing an Application's finalizers through `argocd app patch`, additions included, and applying an inline manifest that names the deletion-approved key or a Redis client, a `--dry-run=server` one or one that only mentions them included, are tasks for a human, as the answer's false positives say. So is a pod whose stdin text names a client, whatever its program, and an `oc create secret` or `configmap` that reads such text on stdin, since every text on an `oc apply`, `oc create` or `oc replace`'s stdin counts as a manifest.
- The gaps that the answer keeps are not checked: a raw socket that speaks the Redis protocol (`printf 'FLUSHALL\r\n' | nc ...` in a pod) or any other program that does; a manifest in a file or a kustomization (`oc apply -f job.yaml`, `-k`), in another command's output (`oc get ... | jq ... | oc replace -f -`) or in an editor (`oc edit`, `argocd app edit`), like the other file-based paths of ADR 0024 §4; a Redis client patched into an existing pod spec (an `oc patch deploy ...` that sets a container's command), which the workload's next pods then run; a variable, a brace list or a glob in the place of a client, a verb or a key (`C=redis-cli; oc exec pod -- $C`, `{redis-cli,x}`, `redis-cl?`), as for every other check; and inline manifests that empty finalizers or set a `Delete` or `Recycle` reclaim policy, which the patch rule does not read.
- Beyond the answer's list, these paths and spellings are not checked either, and need an answer of their own before the hook blocks them (ADR 0001 §6); the tests pin them as allowed. Outside the verbs the answer names: `oc adm must-gather --image=<image> -- <command>`, which starts a pod with that image and command, and `argocd app create -f -` or `-f <(...)`, which reads an Application from the command text and can set the deletion-approved annotation with `--upsert`. Within the gap of a client patched into an existing pod spec: `oc set probe ... -- redis-cli ...` and `oc set deployment-hook ... -- redis-cli ...`. Spellings that the readings of section 3 do not follow: the here-string of a `cat` inside a subshell or brace group whose output is piped on (`{ cat <<< '...'; } | oc exec -i ...`), and a heredoc inside a group whose closing `)` or `}` is not on the line after the body.
- A `<<` that the quoting model is not sure of makes the hook read the command twice (section 3), so a commit message or a file written with a heredoc after a line that the model does not read (one with a backslash, a backtick or `$'...'`, or a heredoc inside an unclosed string) is also read as commands, which errs towards blocking: a message that mentions a blocked command there is refused, as one in `git commit -m '...'` is (the reason says to use `git commit -F <file>`).
- The receiving line of a heredoc is read with its quotes removed, so a commit, PR or issue title that names `oc run`, `oc apply`, `oc create` or `oc replace` makes the body after it count as the pod's stdin or as a manifest (`gh pr create --title "... oc run ..." --body "$(cat <<'EOF'` with a body that names `redis-cli`), as ADR 0035 already let a title that names `oc exec` make the body a script in the cluster. The reasons say to pass such a body from a file (`--body-file <file>`, `git commit -F <file>`).
- An option value with blanks of `oc run` or `oc create` can still shift the NAME in the hook's reading of the words cut at blanks, which errs towards blocking (`oc run --env 'X=a b' redis-cli --image=redis` is blocked).
- A Redis client in `--overrides` JSON, in a manifest or in the text `oc run` passes on stdin is found by its name wherever it stands as a word, in each of the three readings of section 2, so a label, an environment value, a comment or a log line with the name counts too, which errs towards blocking. In the command part of a new pod it counts by its program name, as in `oc exec`.
- The pod-start checks look for Redis clients only. A database command in a new pod keeps the target check that every command word gets, so a `psql -h localhost` there, which reaches the pod's own host, stays allowed, and a database command in an inline manifest or in the stdin of `oc run` is not checked, as before.
- The answer's gaps for text that only the shell computes hold for the new checks, as ADR 0035 says for the old ones.
- website_k8s stays on its older guardrails until its follow-up PR merges.

**What must be true in code and tests**

- The hook blocks every case of section 2 and the spellings of section 3, allows the look-alikes and the texts that only mention the commands, and its tests pass in CI. Removing any one of the new rules or readings from the hook makes a test fail, a block in the tests counts only with the reason of a check, and a mutation check in a scratch copy shows both; the exception is a value option of `oc run` or `oc create` dropped from the hook's list other than `--restart` and `--overrides`, which the tests pin by name: that is caught only when the oc 4.22 client is on the PATH, which it is not in CI, like a boolean wrongly added to the list.
- Every failure path of the hook still exits 2.

## Alternatives considered

| Option | Source | Why not |
|---|---|---|
| Leave all five paths as ADR 0035 records them | third decision register D110, option 2 | An agent could still flush backend2's Redis from an `oc run` pod, or with `redis-benchmark` through the same `oc exec` that refuses `redis-cli`, remove or add an Application's finalizer through `argocd app patch`, and set the annotation with `oc apply`. |
| Block all five, manifest files and shell-computed words included | third decision register D110, option 3 | It turns the hook into a file reader that opens every `-f` file and renders `-k` with `oc kustomize`, which ADR 0024 and ADR 0028 leave out, and must block a file it cannot read; it still cannot see `oc edit`, and its expansion rule would refuse routine work such as `oc patch deploy web -p "$P"`. |
| Block database commands too in a pod the agent starts | not offered; considered while writing this ADR | The answer names Redis clients. A database command there keeps its target check (ADR 0035 §2 item 4), and blocking it always is a new rule that needs another answer (ADR 0001 §6). |
| Apply the whole patch rule, reclaim policy included, to `argocd app patch` | not offered; considered while writing this ADR | The answer names the finalizer match, and `argocd app patch` patches only an Application, which has no reclaim policy. |
| Read a manifest's YAML and look only at container commands and the annotation's key | not offered; considered while writing this ADR | It needs a YAML parser in the hook, for the forms that ADR 0035 §2 already reads as text, and the answer accepts the false positive of a manifest that only mentions the key or a client. |
| Read stdin as a manifest only when `-f` names stdin | not offered; considered while writing this ADR | `-f -`, `-f /dev/stdin`, `--filename=-`, `-f-` and the `/proc` paths all read it, and a text on stdin that oc does not read is a rare command; reading every such text errs towards blocking, as ADR 0028 §4 reads every text that `oc exec` gets. |
| Read the text that `oc run` passes to its pod as commands, as for `oc exec` | not offered; considered while writing this ADR | The answer names the Redis clients, and the pod's program need not be a shell; a shell word in the command already makes the hook read the text as a script. |
| Put the decoded manifest or pod text into the segment as plain words | not offered; considered while writing this ADR | Every other check would read it as words, so a ConfigMap that quotes `oc exec pod -- psql` would count as that command; the base64-encoded synthetic segment keeps the text for the rules of section 2 alone. |
| Deny rules for a Redis client in `oc run` or `oc create`, or for the annotation in `oc apply` | not offered; considered while writing this ADR | A text rule would refuse a pod or image named like a client and a file named like the key, which the hook allows, and would miss the key piped from `cat`; a deny rule without a hook check behind it fails ADR 0035 §4's test. |
| Keep the first-line-only heredoc reading | not offered; considered while writing this ADR | It is a defect of the heredoc rule that ADR 0028 accepted, not a reading: a script for `oc exec` on a later line passed for commands on the host. Fixing an accepted rule needs no new answer (ADR 0001 §5). |
| Find a heredoc only where its `<<` is surely outside quotes | not offered; raised in the review of this change | A real heredoc after quoting that the model does not read (`echo don\'t`, then `oc exec -i redis-0 -- sh <<'EOF'`) would then be lexed as commands on the agent's host, so the script it gives the pod would pass; reading the command both ways errs towards blocking in both cases. |
| Find a heredoc's receiver with the lexer, so that a title which names `oc run` is one word | not offered; raised in the review of this change | The lexer would have to read heredocs before the receivers that decide how it reads them, and `sh -c "oc exec ..." <<'EOF'` and a quoted verb must still count; the false positive is recorded instead, as ADR 0035 records the one for `oc exec`, and the reason says how to avoid it. |
| Record the spellings that the review found as gaps | not offered; raised in the review of this change | The answer is to block what the command text shows. Each of them is a spelling of a reading that ADR 0028, ADR 0035 or this ADR accepted (a heredoc, a here-string, piped text, a script a shell runs, the command part of `oc run`), so reading it is a fix (ADR 0001 §5); only the paths outside the answer's verbs and two rare group spellings stay recorded. |
